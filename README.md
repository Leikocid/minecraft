# Andrew — Minecraft Bedrock Add-On

## 1. Что это

Это Bedrock-аддон `andrew` для игры Minecraft Bedrock Edition.

**Целевые версии:**
- Игра: **1.26.51** (iPad)
- Script API (`@minecraft/server`): **2.10.0**
- Bedrock Dedicated Server в Docker: **1.26.51.1**
- Минимальная версия движка в пакетах: **[1, 26, 50]**

Все версии зафиксированы в `scripts/targets.mjs` — единственный источник истины. Манифесты и конфигурация Docker синхронизируются с этим файлом.

## 2. Требования

- **Node.js** версии 20 или выше
- **Docker** (установлен и запущен)
- **iPad** с установленной Minecraft Bedrock Edition 1.26.51 (для финальной проверки; на Mac Bedrock не доступен)

Цикл разработки:
1. Сборка и статическая проверка на Mac
2. Загрузка пакета в BDS в Docker (проверка логов)
3. Визуальная проверка на iPad

## 3. Команды

### Подготовка и проверка кода

```bash
npm ci
```
Установка зависимостей (чистая установка, как в CI).

```bash
npm run typecheck
```
Проверка типов TypeScript против `@minecraft/server`. Успех — без ошибок компиляции.

```bash
npm test
```
Запуск unit-тестов (`node:test`). Успех — все тесты проходят.

### Сборка

```bash
npm run build
```
Собирает `.mcaddon` в `dist/andrew.mcaddon`: компилирует TypeScript, валидирует JSON манифестов и предметов, упаковывает пакеты. Успех — файл `dist/andrew.mcaddon` существует и архив корректен.

```bash
npm run validate
```
Валидирует JSON манифестов и файлы определений предметов без сборки архива. Успех — вывод `Validation passed` без ошибок.

```bash
npm run build:clean-clone
```
Собирает `.mcaddon` из чистого клона репозитория (в отдельной директории). Проверяет, что процесс воспроизводим и не зависит от состояния рабочей копии. Успех — файл собран без ошибок, архив корректен.

### Сервер BDS в Docker

```bash
npm run bds:check
```
Одноразовая проверка: запускает BDS в Docker, загружает пакет, читает лог на наличие ошибок манифеста/зависимостей и выполнения скриптов, останавливает контейнер. Успех — в логе нет ошибок `manifest`, `dependency`, и скрипт выполнился (найдена строка от `console.warn` или успешное событие).

```bash
npm run bds:up
```
Собирает свежий `.mcaddon`, устанавливает текущие пакеты в мир сервера и запускает BDS в фоне как LAN-сервер (порт 19132/UDP) в режиме Survival с читами. Успех — контейнер запущен, в выводе есть строка `Сервер поднят: <IP>:19132 — ...` (см. раздел 4(б) о доставке на iPad).

### Два сервера: рабочий и QA

Серверов два, и они полностью независимы.

| | Рабочий | QA |
|---|---|---|
| Команды | `npm run bds:up` / `:down` / `:logs` | `npm run bds:qa:up` / `bds:qa:down` / `bds:qa:logs` |
| Адрес для iPad | `<IP>:19132` | `<IP>:19134` |
| Контейнер | `andrew-bds` | `andrew-bds-qa` |
| Порты | 19132 TCP+UDP, 19140–19149 UDP, 7551 UDP | 19134 TCP+UDP, 19150–19159 UDP, 7552 UDP |
| Данные и мир | `docker/bds/data/` | `docker/bds-qa/data/` |

**Зачем.** `npm run bds:check` и `npm run bds:gametest` пересоздают контейнер `andrew-bds` — то есть любая проверка роняла LAN-сервер, на котором в этот момент играют. QA-инстанс проверками не затрагивается никогда: у него другое имя контейнера, и проверочные полосы обращаются только к рабочему.

**Порядок работы.** Новые сборки деплоятся на QA и проверяются там. Рабочий сервер живёт своей жизнью и обновляется отдельно, когда проверенное решено выкатить.

Порты у QA свои и внутри контейнера тоже, и публикуются один в один. Это не косметика: NetherNet сообщает клиенту тот порт, который видит сам сервер, поэтому трансляция «снаружи 19134 → внутри 19132» ломает рукопожатие. Выбор инстанса — переменная `ANDREW_BDS_DIR` (`bds` по умолчанию, `bds-qa` для QA); каталог инстанса несёт свой `compose.yaml`, свой `server.properties` и свой `./data`.


```bash
npm run bds:down
```
Останавливает и удаляет контейнер BDS. Успех — контейнер остановлен, `docker ps` не показывает `andrew-bds`.

```bash
npm run bds:logs
```
Выводит логи работающего контейнера BDS в реальном времени. Используйте для отладки; нажмите Ctrl+C для выхода. Успех — видны логи инициализации и событий.

## 4. Доставка на iPad

Два независимых пути поставить аддон на iPad. Путь (а) — штатный, ничего не меняет на Маке. Путь (б) — для частой проверки новых версий: мир крутится на Маке, iPad один раз добавляет сервер и просто заходит, без повторного импорта файла.

### (а) Импорт `.mcaddon` (штатный путь)

1. Соберите свежий файл: `npm run build` → `dist/andrew.mcaddon`.
2. Перенесите файл на iPad:
   - **По AirDrop** — на Mac откройте `dist/andrew.mcaddon` в Finder, кликните правой кнопкой → `AirDrop` → выберите iPad; на iPad примите файл в Файлах, или сразу откроется Minecraft.
   - **Через Файлы** — скопируйте `dist/andrew.mcaddon` в iCloud Drive / Google Drive или синхронизируйте через Finder; на iPad откройте Файлы, найдите файл, тапните и выберите «Открыть в Minecraft».
3. Minecraft импортирует оба пакета (Behavior + Resource) автоматически.
4. **Если этот аддон уже был установлен раньше** (та же или более старая версия — у пакетов один и тот же UUID), после импорта на iPad может оказаться «дубликат набора», либо новая версия не подменит старую. Перед повторным импортом удалите прежнюю копию: на iPad откройте **Настройки → Хранилище** (Settings → Storage), найдите «Andrew BP» и «Andrew RP» в списке пакетов и удалите их, затем импортируйте новый файл.
5. Откройте мир и включите оба пакета — см. «Включение пакетов в мире» ниже.

### (б) LAN-сервер (без импорта, для быстрой проверки)

Мир крутится на Маке; iPad один раз добавляет сервер по адресу в сети — заново переносить файл не нужно, каждая новая версия уже установлена на сервере при следующем запуске.

1. На Маке выполните:
   ```bash
   npm run bds:up
   ```
   Команда сама соберёт свежий аддон (`npm run build`), установит его в мир сервера и запустит сервер. В конце выведется строка вида:
   ```
   Сервер поднят: 192.168.1.23:19132 — на iPad: Играть → Серверы → Добавить сервер
   ```
   Если IP-адрес Мака не удалось определить автоматически, команда вместо адреса напишет «IP не определён — посмотрите в Настройках macOS → Сеть».
2. На iPad откройте Minecraft, нажмите **Играть** (Play) → вкладку **Серверы** (Servers).
3. Нажмите **Добавить сервер** (Add Server) и заполните:
   - **Имя сервера** (Server Name) — любое, например «Andrew».
   - **Адрес сервера** (Server Address) — IP-адрес из строки на Маке (например `192.168.1.23`).
   - **Порт** (Port) — `19132`.
4. Сохраните и нажмите на появившийся сервер, чтобы зайти. iPad и Мак должны быть в **одной Wi-Fi-сети** (не гостевой и не сотовой).
   Как это устроено (на случай «не подключается»): iPad-клиент 1.26.51 при входе по адресу говорит по **RakNet (UDP 19132)** — сервер поэтому запущен с `transport=raknet`, хотя сам BDS в логе советует NetherNet. На всякий случай опубликованы и NetherNet-порты (TCP 19132, UDP 19140–19149, UDP 7551). Быстрая проверка с Мака, что сервер отвечает через Docker: `node -e` с RakNet-пингом или просто `npm run bds:logs` и попытка входа — в логе должна появиться строка о подключении игрока. Если строк нет вообще, пакеты с iPad не доходят до Мака: проверьте, что оба устройства в одной Wi-Fi-сети (не гостевой) и что на роутере не включена изоляция клиентов.
5. Сервер сам передаёт iPad оба пакета (Behavior + Resource) при входе — вручную ничего включать не нужно.
6. Мир на сервере — **Survival с читами** (доступны команды вроде `/give`) — переплавка в кирке шахтёра проверяется только в Survival, обычное Creative-присоединение её не покажет.
7. Когда проверка закончена, на Маке остановите и уберите сервер:
   ```bash
   npm run bds:down
   ```
   Логи запущенного сервера в реальном времени — `npm run bds:logs`.

## 5. iPad: проверка на устройстве

### Включение пакетов в мире

1. Запустите Minecraft на iPad.
2. Создайте новый мир или откройте существующий.
3. В меню настроек мира:
   - **Behavior Packs**: добавьте «Andrew BP» (behavior pack).
   - **Resource Packs**: добавьте «Andrew RP» (resource pack).
   - Убедитесь, что оба пакета отмечены как включённые (галочка).
4. Сохраните настройки и войдите в мир.

### Проверка логов (Content Log GUI)

1. В игре откройте **Настройки** (Settings).
2. Выберите **Creator** → **Activate Command Block Output** (если нужна сборка команд).
3. Для просмотра логов скрипта:
   - Откройте **Настройки** → **Creator** → включите **Content Log**.
   - На экране появится лог в реальном времени (белый текст на полупрозрачном фоне).
   - Используйте его для отладки ошибок скриптов и импорта пакетов.

Подключение к LAN-серверу описано в разделе 4(б) выше — команда `npm run bds:up` сама выводит адрес и порт для шага «Добавить сервер».

## 6. Паутинный меч (Web Sword)

Легендарное оружие #1. Урон как у обычного алмазного меча (`andrew:web_sword` — без бонуса к урону, без прочности); всё его значение — в способности.

**Крафт.** На верстаке: паутина крестом, алмазный меч в центре —

```
 W
WSW
 W
```

(`W` — `minecraft:web`, `S` — `minecraft:diamond_sword`, любой прочности/зачарования — чары на меч-ингредиент не переносятся). Право крафта — **одно на мир**: первый успешный крафт объявляется в чат («⟨ник⟩ выковал легендарный Паутинный меч!»), меч несёт скрытую метку владельца. Повторный крафт (второй меч в survival-инвентаре при уже потраченном праве) откатывается автоматически: меч изымается, возвращаются 4 паутины и новый алмазный меч, в чат приходит сообщение «Единственный Паутинный меч в этом мире уже существует — ингредиенты возвращены».

**Способность.** Посмотрите на блок или сущность в пределах досягаемости (≤5 блоков по блоку, ≤3 по сущности) и используйте предмет (ПКМ/тап по экрану) — способность ставит куб 3×3×3 из настоящего cobweb вокруг цели, защищая блоки с инвентарём, неразрушимые и спец-блоки (список — `PROTECTED_BLOCK_IDS` в `src/websword/cube.ts`). Cooldown — 30 секунд, таймер виден в actionbar («Паутинный меч: N с» / «Паутинный меч: готов»); повтор до истечения cooldown ничего не делает.

**Смерть и возврат.** Помеченный меч не выпадает при смерти владельца и не может быть подобран другим игроком — он автоматически возвращается владельцу при возрождении («Паутинный меч вернулся к вам»).

**Команда оператора** `/andrew:websword <give|reset> [target]`:
- `give [target]` — выдаёт помеченную тестовую копию (origin=admin); удерживается при смерти как обычная, но право крафта не тратит и не занимает.
- `reset` — сбрасывает флаг «право крафта потрачено» (только так; уничтожение единственного меча само право не возвращает — это осознанное решение против дюпа).

**Известные ограничения:**
- `/give @s andrew:web_sword` в survival (или creative-инвентарь) неотличим от survival-крафта для гейта «один на мир» — используйте `/andrew:websword give` или креатив для тестов, не полагайтесь на `/give` в survival.
- Чары и прочность меча-ингредиента при крафте не переносятся и не восстанавливаются при возврате.
- Правило приоритета «основная/вторая рука» из спеки не реализовано (единственное легендарное оружие v1) — отложено до появления второго оружия.

## 7. Коса бедствия (Scythe of Calamity)

Легендарное оружие #2. Обычный удар как у незеритового меча (`andrew:scythe_of_calamity` — урон и скорость атаки как у `minecraft:netherite_sword`, без прочности); также рубит блоки как алмазная мотыга (используется рецептом ниже как ингредиент). Всё дополнительное значение — в способности залпа.

**Крафт.** На верстаке: золотые яблоки сверху и снизу по центру, обсидиан слева и справа, алмазная мотыга в центре —

```
 G
OHO
 G
```

(`G` — `minecraft:golden_apple`, `O` — `minecraft:obsidian`, `H` — `minecraft:diamond_hoe`, любой прочности/зачарования — чары на мотыгу-ингредиент не переносятся). Право крафта — **одно на мир**, тот же гейт, что и у Паутинного меча: первый успешный крафт объявляется в чат («⟨ник⟩ выковал легендарную Косу бедствия!»), коса несёт скрытую метку владельца. Повторный крафт откатывается автоматически: коса изымается, возвращаются 2 золотых яблока, 2 обсидиана и новая алмазная мотыга, в чат приходит сообщение «Единственная Коса бедствия в этом мире уже существует — ингредиенты возвращены».

**Способность.** Используйте предмет (ПКМ/тап по экрану) без прицеливания на блок или сущность — способность сама выбирает **ближайшую видимую цель в радиусе 20 блоков**: любого игрока или любого живого моба. **Игрок всегда в приоритете над мобом** — даже если моб стоит вплотную, а игрок в пятнадцати блоках: иначе случайный зомби перехватывал бы залп, предназначенный противнику. Среди целей одного вида побеждает ближайшая, при равной дистанции — та, что ближе к направлению взгляда. Игрок, скрытый Тенебром (Shadow Blade), целью не считается; на мобов скрытность не распространяется. Нет ни одной подходящей цели рядом — сообщение «Здесь нет цели», кулдаун не тратится, можно сразу повторить.

Если цель найдена — по ней летят **три виртуальных снаряда** подряд (это не сущности: снаряды нигде не хранятся, они существуют только как расчёт в скрипте, поэтому проходят сквозь стены и блоки не ломают). Каждое попадание снимает ровно **3 HP чистого урона** мимо брони и зачарований защиты и подбрасывает цель примерно на **10 блоков** вверх; три попадания суммарно могут снять 9 HP. Если цель выходит за пределы 20-блочного радиуса до первого попадания — залп срывается без кулдауна; после первого попадания уже запускается полный кулдаун. Cooldown — 30 секунд, тот же actionbar-таймер, что у Паутинного меча («Коса бедствия: N с» / «Коса бедствия: готова»).

**Команда оператора** `/andrew:scythe <give|reset> [target]` — тот же формат, что у `/andrew:websword`:
- `give [target]` — выдаёт помеченную тестовую копию (origin=admin); право крафта не тратит и не занимает.
- `reset` — сбрасывает флаг «право крафта потрачено».

**Известные ограничения:**
- `/give @s andrew:scythe_of_calamity` в survival неотличимо от survival-крафта для гейта «один на мир» — используйте `/andrew:scythe give` (аналог `/andrew:websword give`, уже реализован) или креатив для тестов, не полагайтесь на `/give` в survival.
- Косу нельзя навести вручную: цель всегда выбирает сама способность по правилам выше. Прицелиться в конкретного моба, когда рядом есть игрок, невозможно — игрок приоритетнее.
- Правило приоритета «основная/вторая рука» из спеки не реализовано — отложено до появления второго активного оружия в обеих руках одновременно.

## Структуры: команды оператора `/andrew:structure`

Четыре структуры (Мельница, Дирижабль, Мини-город Хранителя, Мини-бастион) появляются с вероятностью 1–5 % на чанк — ждать их ради проверки долго. Команда даёт построить структуру рядом с собой, найти уже созданные, поднять шанс на время сессии и телепортироваться к ближайшей. Доступна только оператору (как `/andrew:websword`); обычный игрок получит «Команда /andrew:structure доступна только оператору». Все ответы — на языке игры (RU или EN).

Типы: `windmill` (Мельница), `airship` (Дирижабль), `warden_city` (Мини-город Хранителя) — в Обычном мире; `bastion` (Мини-бастион) — только в Незере.

**Как работает генерация.** В спеке структуры должны появляться «при создании мира», как деревни — но стабильный API не даёт такого момента поймать. Вместо этого фоновое задание идёт следом за игроком и обрабатывает чанки по мере того, как тот в них заходит: для ещё не проверенного чанка — один детерминированный бросок на каждый тип структуры, подходящий этому измерению. Если бросок выпал — проверяется пригодность места (ровная суша, не вода/лава, не заденет уже созданную структуру аддона или чужую постройку — по признакам блоков, ванильный API «тут что-то есть?» не спрашивает) и резервируется запись в реестре, чтобы два одновременных обхода не создали дубль. Прошедший чанк отмечается посещённым в битовом наборе, который переживает рестарт сервера — второй раз он не проверяется, даже если в прошлый раз ничего не поставили. Со стороны это выглядит как обычная генерация: структура стоит там, где её нашли, и не двигается; отличия от ванильной генерации и два непроверенных зондом предположения — в [отчёте об отклонениях](#отчёт-об-отклонениях) ниже.

> **Пока вместо настоящих структур стоит тестовая коробка.** Шаблонов четырёх структур в аддоне ещё нет: каждый тип ставит каменную коробку 9×5×7 с двумя сундуками (лут — из таблицы своего типа: своя таблица у Мельницы и Дирижабля, ванильная Ancient City у Города Хранителя, ванильные бастионные — у Бастиона), спавнером зомби и визгуном. Сама по себе такая коробка в мире не появляется — только по `place` или после `chance`. Путь создания при этом настоящий: реестр, проверка места, резерв записи, постановка, заполнение сундуков, состояние «готово».

**1. Поставить у себя — `place <тип> [поворот]`.** Встаньте на ровное сухое место и введите:

```
/andrew:structure place windmill
/andrew:structure place airship 90
```

Поворот — `0`, `90`, `180` или `270`; без него — случайный. Высоту выбирает та же проверка места, что у естественной генерации: Мельница — на земле, Дирижабль — на 40–70 блоков выше рельефа, Город Хранителя — под землёй (верх на Y −35…−45), Бастион — на полу Незера. В чате должно появиться:

> Построено: «Мельница», центр 120 64 -35, поворот 90°, состояние: готово
> У структуры «Мельница» пока нет своего шаблона: вместо неё стоит тестовая коробка с двумя сундуками

Если место не годится, команда скажет почему и ничего не построит, например: «Структуру «Мельница» здесь поставить нельзя: земля слишком неровная» (ещё бывает: вода или лава под ней, мешает спавнер / ванильная структура / постройка игрока, рядом другая структура аддона). Повтор на том же месте: «…она заденет «Мельница» в точке …». Бастион в Обычном мире: «Мини-бастион» строится только в измерении «Незер».

**2. Найти — `locate [тип]`.**

```
/andrew:structure locate
/andrew:structure locate windmill
```

Без типа — список всех типов с числом созданных («Мельница: 2», «Дирижабль: 0», …) или «В этом мире ещё не создано ни одной структуры». С типом — ближайший экземпляр в вашем измерении: «Ближайший экземпляр «Мельница»: 120 64 -35, до неё 48 блоков, состояние: готово», или «В этом измерении ещё не создано ни одной структуры «Мельница»».

**3. Поднять шанс на сессию — `chance <тип> <0-100>`.** Проверка самой генерации, а не только содержимого:

```
/andrew:structure chance airship 100
/andrew:structure chance airship
```

С числом — шанс «сколько на 100 чанков» до перезапуска сервера: при `100` структура появляется в каждом подходящем чанке, куда вы дойдёте; при `0` — нигде. Ответ: «Дирижабль»: 100 на 100 чанков до конца сессии (обычно 2). Не сохраняется — после перезапуска сервера вернётся обычный шанс. Без числа — сразу вернуть обычный шанс. Важно: бросок делается только для чанков, где ещё никто не был; пройденные в это время чанки остаются такими, какими выпали.

**4. Телепорт — `tp <тип>`.**

```
/andrew:structure tp windmill
```

Переносит к ближайшему созданному экземпляру, над его центр, с медленным падением на 10 секунд (Город Хранителя под землёй — на поверхность над ним). Ответ: «Телепорт к структуре «Мельница»: 120 70 -35».

## Зонд движка

Что BDS 1.26.51.1 со стабильным `@minecraft/server` 2.10.0 умеет и не умеет по части структур, измерено зондом strf-p006 перед этапом четырёх структур. Отчёт: [`docs/structures/probe-results.md`](docs/structures/probe-results.md) — 11 вопросов с PASS/FAIL и числами.

Коротко:
- `structureManager.place` сохраняет сундуки и спавнеры и корректно поворачивает шаблон; шаблон 35×30×35 ставится за ~38 мс.
- `/loot insert` через `runCommand` работает с ванильными таблицами.
- `fillBlocks` берёт не больше 32 768 клеток за вызов.
- В одной строке динамического свойства помещается до 32 767 байт.
- Ticking area — не больше 10 на мир.
- В незагруженном чанке `getBlock` возвращает `undefined`, а `getTopmostBlock` бросает исключение.

Зонды запускаются в `npm run bds:check` и `npm run bds:gametest`, их строки начинаются с `[probe] Qn RESULT`.

## Отчёт об отклонениях

Чем генерация структур на самом деле отличается от того, что написано в спеке (появление не при создании мира, а при обнаружении чанка игроком; отсутствие запроса о ванильных структурах; предположения, которые зонд не проверил) — простым языком, для того, кто будет играть и спрашивать «почему не работает»: [`docs/structures/deviations.md`](docs/structures/deviations.md).

## 8. Ошибки версии или зависимостей

Если при импорте `.mcaddon` на iPad или в BDS появляется ошибка вроде:
- `Unsupported version: ...`
- `Missing dependency: @minecraft/server ...`
- `Pack format version mismatch`

**Правило:** прочитайте текст ошибки полностью и откорректируйте целевые версии в `scripts/targets.mjs`, затем пересоберите:

1. Откройте `scripts/targets.mjs`.
2. Обновите одну из трёх констант:
   - `MIN_ENGINE_VERSION` — если ошибка про версию движка
   - `SERVER_API_VERSION` — если ошибка про `@minecraft/server`
   - `BDS_VERSION` — если ошибка в Docker про версию сервера
3. Запустите `npm ci && npm run build` и повторите проверку.

**Важно:** не включайте Beta или Preview API (`-beta.N`, `-preview.N`) для облегчения ошибок. Это скроет реальную несовместимость вместо её исправления. Целевые версии должны точно совпадать с тем, что установлено на устройстве.

│   ├── bds-check.mjs               Одноразовая проверка BDS и логов (creative)
│   ├── bds-up.mjs                  Сборка + запуск LAN-сервера (survival + читы)
│   └── bds.sh                      Управление Docker контейнером BDS (up/down/logs)
├── src/
│   └── main.ts                     Точка входа скрипта TypeScript
├── tests/
│   └── *.test.mjs                  Unit-тесты
├── packs/

│   │   ├── manifest.json           Manifest behaviour pack

│   │   ├── scripts/                Собранный вывод TypeScript (gitignored)
│   │   └── texts/                  Локализация (en_US.lang, ru_RU.lang)
│   └── resource/
│       ├── manifest.json           Manifest resource pack
│       ├── textures/               Иконки и текстуры
│       ├── texts/                  Локализация (en_US.lang, ru_RU.lang)
│       └── particles/              (если есть кастомные частицы)

**Ключевые файлы:**
- `scripts/targets.mjs` — обновляйте версии только здесь
- `packs/behavior/manifest.json` и `packs/resource/manifest.json` — синхронизируются с `targets.mjs` при сборке
- `src/main.ts` — основной скрипт; компилируется в `packs/behavior/scripts/main.js`
- `.mcaddon` — это обычный ZIP-архив с обоими пакетами; можно распаковать для отладки

---

**Начало работы:** `npm ci && npm run build && npm run bds:check` запустит полный цикл сборки и проверки на Mac и в Docker.

## Готовые сборки

`releases/` — собранные `.mcaddon`, которые уже проверялись на сервере и iPad; имя файла несёт версию пакета из манифеста (`andrew-0.1.0.mcaddon` — этап 0, тестовый предмет; `andrew-0.2.0.mcaddon` — этап 1, Кирка шахтёра; `andrew-0.2.1.mcaddon` — новая иконка кирки; `andrew-0.3.0.mcaddon`…`0.3.2.mcaddon` — этап 2, Паутинный меч; `andrew-0.4.0.mcaddon`…`0.4.2.mcaddon` — этап 3, Коса бедствия; `andrew-0.5.0.mcaddon` — каркас четырёх структур: генерация, реестр, лут и команды оператора, но пока на пробном шаблоне — ни одной настоящей структуры ещё нет). Версию во всех манифестах и package.json меняет одна команда: `npm run version:set -- 0.5.1`. Свежую сборку всегда даёт `npm run build` → `dist/andrew.mcaddon`; в `releases/` и на `~/Desktop/andrew-<версия>.mcaddon` кладётся копия того, что реально отдавали на устройство (`cp dist/andrew.mcaddon releases/andrew-<версия>.mcaddon && cp dist/andrew.mcaddon "$HOME/Desktop/andrew-<версия>.mcaddon"`).
