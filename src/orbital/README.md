# Orbital Cannon — deviations from the spec (C-16, `L0-orbc-r013`)

Each line is what ships in this module today, with the KV id that owns it.

1. **Custom item with the fishing-rod icon** (`L0-xcx13`). `andrew:orbital_cannon` is a custom item whose icon is the vanilla `fishing_rod` atlas entry; it is not a real fishing rod, because stable API cannot switch fishing off on one. It casts no line, has no durability and takes no enchantment.
2. **Input by `playerSwingStart`, and what a touch gives** (`L0-xcx8`, `L0-xcx14`, `L0-xq5`). Stable 2.10.0 has no LMB/RMB input event. RMB is `itemUse` (in the air) or `itemStartUseOn` (on a block — the Cannon raises neither `itemUse` nor after-`playerInteractWithBlock` there). LMB is `entityHitBlock` (a block the client picked) or `playerSwingStart` with `swingSource: Attack` plus the view ray — the only signal for a swing that hits nothing, at any distance. LMB fires only with the Cannon in the main hand (`L0-lgnd-as14`). While it is in the main hand no block breaks, in any game mode (`L0-orbc-as05`): the Cannon cannot mine. Measured on BDS with a SimulatedPlayer; what the iPad touch client sends — a tap versus a hold, a swing on a miss, at 6–10 blocks — is not observed (`L0-orbc-ac08`, iPad).
3. **Aim point on touch** (`L0-orbc-cx02`, `L0-orbc-ad01`). The target is the event's own block when the event names one within 25 blocks of the eyes, else the view ray (`maxDistance 25`, liquids and passable blocks skipped). On the default touch layout the block under the finger arrives with the event; a press that names no block aims from the screen centre. Distance is measured to the block's geometry, never through `BlockRaycastHit.faceLocation`.
4. **Nether ceiling** (`L0-orbc-cx03`, ruled by `L0-adr-oded` §2). The spawn height is the target +10, clamped to `heightRange.max − 1` = 127. A target high enough to put that cell in the bedrock roof (y ≥ 113) spawns its charge inside the roof, and it detonates there at once with the roof cell as its point — for both modes, no special case.
5. **The charge is moved by script, not by physics** (`L0-orbc-ad02`, `L0-orbc-as02`). `andrew:orbital_charge` has no gravity, no collision, a 0×0 box and ignores damage, so entities and blasts never move it. It runs as the `minecraft:snowball` runtime class: without one, BDS ticks it as a generic actor that pushes every pushable mob its box overlaps (a cow 0.12 in one pass). What the class changes in the iPad's rendering is not observed. One shared `system.runInterval(step, 1)` exists only while some attack has a charge; each tick it teleports every charge `FALL_SPEED` = 1 block down and reads every cell between the old and the new y, so no block is skipped at any speed. Entities are never queried: players, mobs and boats do not stop a charge, liquids do not either. There is no client interpolation guarantee: on the iPad the charge may look stepped at 20 moves per second (not observed).
6. **Charges are lost on unload and restart** (`L0-orbc-r011`, `L0-orbc-ad03`, §11). Attacks live in memory only (`activeAttacks()`), nothing is persisted, and nothing is refunded. There is no ticking area and no force-load. A charge whose entity turns invalid, or whose next cell is unloaded, is dropped with no effect. The saved entity is removed when it next loads (`entityLoad`), and every charge entity is removed a tick after the world starts: an orphan never detonates.
7. **One scope per script runtime.** Attack ids are `<scope>-<tick>-<seq>` and the charge carries `andrew:oc_attack:<id>`. A runtime's `entityLoad`/`entitySpawn` sweep removes a charge with no attack tag and a charge of its own scope that no live attack holds; a charge of another scope is left to its runtime. The release pack is `oc`; the GameTest pack, which shares the world with it, is `gt`. So a charge hand-tagged with a scope nobody owns stays until the next world start.
8. **A 400-tick safety timeout** (`L0-orbc-p002`). Charges still falling 400 ticks after firing are removed as lost, with a warning in the log. It guards against a stuck path; a normal fall ends within ~120 ticks (End, +60 down to the Void from y 60).

## LMB penetrator (`penetrator.ts`) — deviations (PN-6, `L0-pntr-cons`)

Measured on BDS 1.26.51.1 (Rosetta, the dev Mac); the probes are `probe_pntr_*` in `src/gametest/penetrator.ts`.

1. **The keep list is a list, not a hardness query** (`L0-xasm6`, `L0-pntr-r002`). Stable 2.10.0 has no hardness or "unbreakable" query, so `PENETRATOR_KEEP` in `penetrator-keep.ts` is the only way to spare engine-protected blocks: a Survival-unbreakable block missing from it is removed. xasm6 names the light block once; a placed one is `light_block_<level>` (setting `minecraft:light_block` reads back as `light_block_0`), so all sixteen levels are listed.
2. **Item frames** (`L0-pntr-cx01`, settled by `L0-adr-oprt` §3). A frame in a planned cell goes through `protectLegendariesIn` like a container: lgnd breaks it open with `setblock … destroy` (that break sound and its particles are the engine's, not a second pntr sound), a legendary is moved out, and whatever else spilled — the frame's own item and its contents — is removed with the column. A frame outside the column that loses its wall pops by vanilla rules (`L0-pntr-as06`).
3. **Nested storage items** (`L0-pntr-as05`). pntr hands lgnd only the cell; a legendary inside a bundle or shulker-box *item* in a column container survives only as far as lgnd can read nested storage, otherwise it goes with the container.
4. **Waterlogged cells** (`L0-pntr-as04`). The solid part goes and the cell becomes a `minecraft:water` source — a waterlogged container too, after protection. Which types can hold water is the engine's answer, `canContainLiquid(Water)` on each type's default permutation, read once at world load (714 ids); a type that holds water only in a non-default state is removed like stone and its water with it.
5. **Holders the API cannot read stay** (PN-5, C-15 rank 1 over rank 4). A crafter, a decorated pot and a shelf have no `minecraft:inventory` in 2.10.0, so `protectLegendariesIn` refuses them and the cell is kept (`keptProtectFailed`). The same holds for any holder whose protection throws: the cell and its contents stay, the error goes to the log, the column goes on below.
6. **A chest half paired beyond the plan stays.** Either half of a double chest reports both halves as its container (54 slots), and `setType` on a paired half spills that half's items (38 item entities in an earlier run of `pntr_hard_blocks_no_drops`). A half whose same-type neighbour lies outside the plan is kept (`kept`), untouched; a pair wholly inside the plan is protected, emptied and removed.
7. **Protection per holder cell, not once over the footprint** (`L0-adr-oprt` §1 asks for one call over the column's footprint). The footprint is a 7×7 box: one call would break frames and empty chests in its unplanned cells, and one unloaded chunk or one crafter would refuse the whole column. Each holder gets its own call in the same synchronous step as its `clearAll` and `setType` (`L0-pntr-r005`), with `avoid` = every live column within 24 blocks in the dimension, so a drop never lands in a neighbouring shaft (`L0-pntr-ac04`). Items already lying in the column are not touched (`L0-pntr-r005`).
8. **The ad01 hybrid, taken because the measurement failed PN-1** (`L0-pntr-as03`; `L0-pntr-ad01` rejected alternative 1). The per-cell job as ad01 wrote it (`getBlock` → classify → `setType`, yield every 512 cells) measured 20–23 µs a cell, 13 µs of it reading, so `runJob`'s ~25 ms a tick moved 1,000–1,500 cells: ticksUsed 3–4 for a column at y=76 (PN-1: ≤ 3), 7–10 at y=319 (≤ 6), 7 each for three at once (≤ 6). as03's 2,000 cells a tick does not hold on this host. Now each step of whole bands does: one native query counting the keep set and liquids, one native query finding holders and water-holding types — those go cell by cell as above — then `fillBlocks` air over the planned x-runs (merged down through the bands that repeat them), excluding air, the keep set, liquids and any cell a cell-by-cell step left standing. Nothing drops: a holder is emptied before its `setType` (a chest, a barrel, a shulker box, a furnace that had smelted), and `fillBlocks` over the rest (a spawner, obsidian, reinforced deepslate, a lit portal) gives no item and no XP — `pntr_hard_blocks_no_drops` counts zero new item and XP entities around the column. A query costs its type list, not its volume (0.91 ms with the 714 ids over 7×7×4 or 7×7×161; 0.05 ms with the 23 keep ids; 0.06 ms per row fill), so there is one query per step, and a step is about `CELLS_PER_SLICE` = 512 cells.
9. **One shared interval, not a `runJob` per attack** (`L0-pntr-ad01` names `runJob`; PN-2 wins, `L0-pntr-cons`). On this host the tick after a `runJob` is queued overruns by 15–30 ms even when the job does nothing: a detonation that queues one measured 64–83 ms, one that finishes in its prefix 44–56 ms, against idle ticks up to 56 ms (`probe_pntr_det_tick`, stamps taken where the detonation runs). So the steps run from one `system.runInterval`, alive only while a column is being removed (the flight's pattern), round robin over the live columns within `REMOVAL_MS_PER_TICK` = 25 ms of script a tick (25–35 ms a tick under `runJob` left the ticks at 49–52 ms). The detonation tick removes the top 16 layers synchronously, from a microtask queued in `onDetonate`: still that tick, but after every charge the flight lands in that step has registered its column, so same-tick columns protect with one `avoid` box. Measured (`pntr_budget_measured`): ticksUsed 3 at y=76, 5 at y=319, 4–5 each for three at once; the top 16 layers gone in the detonation tick every time; no tick slower than the idle server's own worst tick over 200 idle ticks — idle ticks on this host already reach 52–57 ms, so a bare 50 ms bar would fail with no attack at all. PN-1 and PN-2 both hold; PN-1 is not relaxed.
10. **The wave is a 20-tick `runInterval`** (`L0-pntr-ad03` allows it): a `runJob` generator is resumed many times per tick and cannot pace one step per tick. Step 0 plays in the detonation tick; a column shorter than 20 layers repeats its last layer, so every one of the 20 ticks shows particles.

## RMB rings (`ring.ts`) — deviations (RG-6, `L0-ring-cons`)

Measured on BDS 1.26.51.1 (Rosetta, the dev Mac); the probe is `probe_ring_drops` in `src/gametest/ring.ts`. `ring.ts` carries the same list next to the code.

0. **Power per ring, and a minimum range** (§10 and §6, amended by
   `decision-ring-power-per-ring-4-4-2-1-1`). The rings explode at 4/4/2/1/1
   from the centre outwards, not all at 4, and the rings refuse a target nearer
   than `RING_MIN_RANGE` = 7. Three measurements decide these numbers, and all
   three contradict the arithmetic one would guess:
   - equal blasts in one tick do not stack — four power-4 blasts 7 blocks away
     hurt an entity once, for 6.1 — but every blast **stronger than the previous
     one** lands again (`probe_blast_stacking`), and a ring attack's cells stand
     at many distances, so a victim takes a rising sequence of 2 to 6 hits;
   - what that costs, measured with the shipped powers
     (`probe_ring_damage_by_distance`): 8 blocks from the target 20 in six hits
     and death, 10 blocks 11, 12 blocks 7, **14 blocks 20 and death** because a
     cell sits under the victim's feet (a power-1 blast at zero distance does
     13.0, at one block 4.0), 16 blocks 1.9, and nothing at all from 18 out;
   - a blast's hole is not 1.3 × power (`probe_crater_by_power`): on soil power 4
     breaks 133 cells and reaches 5.0, power 2 breaks 38, power 1 breaks 9, power
     0.5 breaks none; **in stone power 1 breaks nothing at all**, so the two
     outer rings mark soil and leave rock untouched.

   So the minimum buys a shot one can walk away from, not one that can be watched
   from the spot: three seconds of fuse and a few steps put the shooter past 18.
   The penetrator has no minimum — it does no entity damage.

1. **Queue delay** (`L0-ring-ad02`, `L0-ring-p003`). A charge is removed at contact and its blast follows from one FIFO queue shared by every attack, `RING_MAX_BLASTS_PER_TICK` = 48 a tick, each at its own ring's power. The first drain runs from a microtask queued by `onDetonate` — the contact tick, after the flight step that landed it, so all of that tick's contacts share one protection call — and one `runInterval` drains the rest, existing only while the queue is not empty. A 201-charge attack on flat ground takes 5 ticks (48/48/48/48/9); three fired together take 13. A blast queued over 200 ticks is dropped and logged.
2. **The `doTileDrops` gate and its one owner** (`L0-ring-ad01`, `L0-adr-odrp` §5). Each queue step reads the world rule, sets it false, makes its `createExplosion` calls and writes back the value it read, in `finally`, inside one synchronous stack — so an admin's `false` stays `false` and the world is never saved with the toggled value. `ring.ts` is the only product file that writes the rule (a node test greps `src/` for any other writer; the ring GameTest sets `false` by command to test that start). Measured (as01): a script `createExplosion(…, 4)` with the rule on drops what it breaks (32 dirt from a 9×9 dirt pad) and spills a destroyed chest. Inside the window (as02) the dirt and stone drop nothing, a killed zombie still drops its loot and a killed player its 5 diamonds (`doMobLoot`, `keepInventory` untouched). World TNT a ring blast primes goes off ticks later, after the window, and drops as vanilla TNT (`L0-ring-as07`).
3. **Item frames** (`L0-ring-r008`, `L0-adr-oprt` §3). `protectLegendariesIn` breaks every frame within ±8 of a step's blasts with `setblock … destroy` before the window opens, so the frame and its item spill as ordinary items (a legendary among them is moved). A frame inside ±8 but beyond the blast's reach is broken too.
4. **Nested storage** (`L0-lgnd-cx12`). A legendary inside a shulker-box or bundle *item* in a container survives only as far as lgnd reads nested storage; otherwise it goes with the container.
5. **Container fallback: on** (`L0-ring-as02`, `L0-ring-ent3`). The rule does not stop a destroyed container's contents: a chest with 10 cobblestone destroyed by one ring blast under `doTileDrops=false` spilled all 10 (as02). So each step counts the contents of every script-readable container within ±8 of its blasts, after protection, and after the window removes new items of those types within 1 block of a container cell the blasts destroyed, up to those counts (a double chest counts once), never a legendary. An item of the same type lying there before the step is kept; a spilled item that a later blast of the same step threw further than a block stays; one that a later blast destroyed is simply gone (in a full ring most spills are).
6. **No `source`** (`L0-ring-r004`, `L0-ring-as03` failed). The spec wants the owner as the explosion's source for kill credit only, never as an exemption, and as03 assumed the engine agreed. It does not: a zombie that is its explosion's `source` took no damage at 4 blocks, while the same blast without a source killed an identical zombie (23.5 and 23.1 damage; `probe_ring_drops`, twice). So no ring blast names a source, and the owner takes TNT damage like anyone else (`ring_tnt_damage`, the zombie-owner run). A kill by the rings reads "blown up", never "blown up by <owner>", and **a mob the rings kill drops its loot but no XP**: Bedrock drops XP only for a kill credited to a player — a zombie 2 blocks from TNT a SimulatedPlayer lit with flint and steel dropped 3 orbs, one by TNT spawned primed by script and one by a ring blast none (`probe_ring_drops`, xp) — and only `source` would credit the owner (`L0-ring-r006` and `L0-ring-ac18` expect the XP; the task's as03 rule removes the source). The engine also refuses a GameTest SimulatedPlayer as a source outright (`TypeError: Native optional type conversion failed … expected type: Entity`, for the handle and for `world.getEntity`'s answer alike), so a player source could not have been measured on BDS anyway.

7. **Budget at the starting cap** (`L0-ring-as05`, RG-1…RG-3; `ring_three_budget`). Three RMB fired in one tick, targets 16 apart so the footprints overlap by 13: all 603 contacts land in one tick, the queue explodes 48 a tick and is empty 13 ticks later (per attack 5, 9 and 13 ticks, FIFO). Server tick wall time from the first contact tick: max 66 ms, never two ticks in a row over 50 ms. The same host idle, 200 ticks: max 63 ms, 76 of the 200 over 50 ms, up to 3 in a row — tick wall time is paced to 50 ms, so a bare "over 50 ms" counts jitter. The GameTest holds a tick as slow only above both 50 ms and the idle server's own worst tick (the `pntr_budget_measured` bar) and logs the bare 50 ms count beside it. RG-2 and RG-3 both hold at 48, so the cap is not lowered. 60 ticks after the shots neither the ring queue interval nor the flight interval runs.

8. **Damage is the engine's TNT damage** (`L0-ring-r004`, `L0-ring-ac13`; `ring_tnt_damage`, `probe_ring_drops` height). One ring blast against one primed vanilla TNT held on the same cell, a SimulatedPlayer and a zombie at 3, 5 and 7 blocks: 29.11/29.13, 31.00/31.01, 15.29/15.29, 16.54/16.89, 4.86/4.86, 6.11/6.11 (explosion damage from the hurt events). None of the ring's flags changes it (a player at 7 blocks takes 4.86 with every combination of `breaksBlocks`, `allowUnderwater`, `causesFire`), and the centre half a block lower gives 4.94. Health read back tens of ticks later undercounts a player by whole hearts — SimulatedPlayers regenerate — which once made the ring look 2 HP weaker; the GameTest counts the hurt events, and a death as all the health there was. Underwater, a blast with `breaksBlocks: false` changes no block and deals the same damage whether `allowUnderwater` is true or false (as04).
