# ADR — The four templates are `.mcstructure` files generated by a Node script from checked-in layout sources

**Status:** accepted 2026-09-26 (strf-p006). See `decision-adr-l0-adr-tmpl-accepted-zond-strf-p006-q1-q2-q3`.

## Context
- Every structure is "один фиксированный шаблон" (§2), with fixed chest, spawner, shrieker and door positions that tests count exactly (tests 16–17, 28–29, 47–48, 55–57).
- Hardware: Mac mini + iPad, no Windows, no Bedrock client on macOS (v1 intent). Hand-building in-game and exporting with a structure block is impractical. A `/structure save` result lives inside the world's LevelDB, not in the pack.
- C-8: the build must be reproducible from a clean clone.
- Spawner mob type and shrieker `can_summon` are block-entity or state data. The stable Script API cannot configure a spawner's entity at runtime.

## Decision
- Keep each template as **code/data in the repo**: layered block palettes or builder functions in TS/JSON.
- `scripts/build-structures.mjs` compiles them into little-endian NBT `.mcstructure` files under `packs/behavior/structures/andrew/`. It includes block entities: chest (empty, loot filled by script), `mob_spawner` with `EntityIdentifier`, and block states (`can_summon`, door halves, wheat `growth`, rotated stairs).
- A unit test round-trips each file and asserts the counts the spec fixes: chests per floor/room, spawners, shriekers, doors, footprint bounds.
- A BDS test places each template in 4 rotations and re-counts in-world.

## Rejected alternatives
- **Build in-game on the iPad and export.** Not reproducible. Export tooling needs Windows or LevelDB extraction.
- **Runtime block-by-block placement from a JS layout, no `.mcstructure`.** Cannot set spawner entity type on stable APIs. It is also slower (thousands of `setPermutation` calls per Windmill). Kept as the fallback for plain blocks only.

## Consequences
- `infr` gains an NBT writer and a template test suite. The visual review of all four identities stays on the iPad (C-9).
