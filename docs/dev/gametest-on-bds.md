# GameTest с симулированным игроком на BDS

Разведка по задаче GAMETEST-01: можно ли гонять сценарий «Кирки шахтёра» на
Bedrock Dedicated Server 1.26.51.1 в Docker без человека и без iPad.

## Вердикт: да, работает

Симулированный игрок на BDS ломает железную руду нашей киркой и получает
железный слиток, ломает камень и получает булыжник, кирка при этом не
изнашивается. Человек в проверке не участвует.

```
onTestPassed: andrew:pickaxe_autosmelt
onTestPassed: andrew:pickaxe_keeps_vanilla_drops
```

Команда — `npm run bds:gametest`, выход 0 при успехе, 1 при любом провале.
Полный лог сервера остаётся в `dist/bds-gametest.log`.

После починки двух дефектов ниже — три подряд полных прогона (со сборкой),
3 из 3 с кодом 0 и обоими пройденными тестами. До починки прогон плавал:
на одном и том же коде autosmelt то проходил, то падал.

Граница C-2 соблюдена: beta-модуль `@minecraft/server-gametest` есть только в
`packs/gametest/` и `src/gametest/`, эксперимент включается только в отдельном
мире `gametest`. Продуктовые пакеты и мир `andrew` не затронуты, в
`dist/andrew.mcaddon` dev-пакет не попадает.

## Как включить эксперимент на BDS

Штатного способа нет: ни ключа в `server.properties`, ни переменной окружения у
образа `itzg/minecraft-bedrock-server`. Флаг лежит в `level.dat` мира, а мир
появляется только после первого старта сервера. Отсюда двухфазный запуск в
`scripts/bds-gametest.mjs`:

1. поднять сервер «пустым», чтобы движок создал мир `gametest`;
2. остановить его, пропатчить NBT в `worlds/gametest/level.dat`, поднять снова.

В компаунде `experiments` выставляются три байта: `gametest` (внутренний ключ
той самой галки, которая в UI называется «Beta APIs» — ключ не переименовывали),
`experiments_ever_used` и `saved_with_toggled_experiments`. Без двух последних
мир не считается экспериментальным.

`level.dat` — это little-endian NBT с 8-байтовым заголовком (версия формата,
длина тела). Готовой зависимости для этого не взято, парсер и сериализатор
написаны в скрипте (~120 строк) — round trip сохраняет типы тегов, а частичный
разбор считается ошибкой и рушит запуск, чтобы не обрезать мир молча.

Движок подтверждает результат на следующем старте:

```
[2026-09-20 20:46:05:811 INFO] Experiment(s) active: gtst
[2026-09-20 20:46:06:464 INFO] Pack Stack - [01] Andrew GameTest BP (id: b1958c0d-1533-441c-af3b-da9310f792ca, version: 0.2.0) @ behavior_packs/andrew_gametest
[2026-09-20 20:46:07:053 WARN] [Scripting] [gametest] script loaded
```

## Что пришлось обойти

### Консоль сервера под Rosetta

Скрипт `send-command` из образа ищет процесс сервера через
`readlink(/proc/<pid>/exe)`, а под Rosetta это у всех процессов
`/run/rosetta/rosetta` — совпадения не будет никогда. Процесс ищется по
`cmdline`, команда пишется ему в stdin (`/proc/<pid>/fd/0`).

### Структура-площадка

`register()` не запускает тест без `structures/<class>/<name>.mcstructure` в
пакете. Площадка 7×5×7 (каменный пол, воздух выше) генерируется тем же скриптом,
а не лежит бинарником в репозитории — иначе она молча разъехалась бы с
координатами в `src/gametest/main.ts`.

### setBlock падает, когда менять нечего

Главная поломка разведки. Контрольный тест ставил камень и получал:

```
onTestFailed: andrew:pickaxe_keeps_vanilla_drops - Could not setBlock 'stone'
```

Первая гипотеза (площадка вне тикающей зоны) оказалась неверной. Диагностический
тест перебрал шесть блоков по трём координатам, 36 наблюдений:

```
[probe] setBlockType FAIL minecraft:stone @ 3,1,3: GameTestError: gameTest.assert.couldNotSetBlock
[probe] setBlockType FAIL minecraft:stone @ 2,1,3: GameTestError: gameTest.assert.couldNotSetBlock
[probe] setBlockType ok   minecraft:stone @ 3,2,3
[probe] setBlockType ok   minecraft:cobblestone @ 3,1,3
[probe] setBlockType ok   minecraft:iron_ore @ 3,1,3
```

Камень ставится (строка 3), а `3,1,3` принимает и булыжник, и руду (строки 4–5)
— значит дело не в блоке и не в координате. Единственное, что отличает провал от
успеха: **вызов не меняет блок**. `setBlockType` бросает
`gameTest.assert.couldNotSetBlock`, когда блок уже такой, какой просят; «ничего
не изменилось» и «не смог» движок сообщает одинаково. Пол площадки каменный,
поэтому «поставить камень» на нём — no-op, а «поставить руду» — нет.

Отсюда же второй факт: нижний слой структуры движок кладёт на относительный
`y=1`, а не `y=0` (камень есть на `3,1,3` и `2,1,3`, воздуха нет; на `3,2,3`
воздух). Игрок теперь ставится на `y=2` — на пол, а не внутрь него.

Лечится проверкой перед установкой — `placeBlock()` в `src/gametest/main.ts`.

### Мир по умолчанию — океан, и прогон плавал

Один и тот же код давал то зелёный, то красный прогон:

```
onTestFailed: andrew:pickaxe_autosmelt - Expected Item Entity of type item.iron_ingot
```

GameTest ставит площадку в точке самой консоли, а в обычном мире это «где
сгенерировалось». Диагностика показала, где именно:

```
[probe2] minecraft:iron_ore poll=1 ... player=3.5,53.0,8.5 items=[minecraft:kelpx1@1.7,52.8,1.8 | minecraft:kelpx1@6.3,57.5,6.8]
```

`y=53` при уровне моря 62 и плавающая ламинария — площадка под водой. Под водой
добыча впятеро медленнее, и игрок начинает тонуть внутри бюджета теста (400
тиков), поэтому руда (твёрдость 3) укладывалась в бюджет не всегда, а камень
(1.5) почти всегда. Отсюда «плавающий» результат, а не отдельный баг.

Лечится суперплоским миром — `BDS_LEVEL_TYPE=FLAT` в `docker/bds/compose.yaml`
(только для мира `gametest`; `bds:check` и `bds:up` остаются на `DEFAULT`).
После этого площадка каждый раз на суше и посторонних сущностей рядом нет:

```
[probe2] minecraft:iron_ore poll=1 ... player=3.5,-58.0,8.5 items=[]
```

## Найдено попутно, не чинилось

В продуктовом скрипте приветствие падает на симулированном игроке:

```
[2026-09-20 20:55:53:167 ERROR] [Scripting] [Andrew BP] TypeError: cannot read property 'sendMessage' of undefined    at <anonymous> (main.js:52)
```

`world.afterEvents.playerSpawn` в `src/main.ts:15` приходит с `event.player ===
undefined`, когда игрока породил `spawnSimulatedPlayer`. На тесты это не
влияет (обработчик отдельный, оба сценария проходят), но в логе сервера
исключение сыплется на каждый спавн. Не тронуто сознательно: задача —
разведка, а критерий приёмки требует, чтобы продуктовые пакеты остались без
изменений. Чинить отдельной задачей в `src/main.ts`.

## Цена поддержки

Разовая цена уже уплачена: `scripts/bds-gametest.mjs` ~615 строк, из них ~120 —
NBT-парсер, который нужен только потому, что у BDS нет ни ключа для
экспериментов, ни способа подсунуть структуру.

Дальше платить придётся за это:

| Что | Когда ломается | Чем чинить |
|---|---|---|
| Версия `@minecraft/server-gametest` | каждый релиз игры | перепинить по dist-tag `beta` (сейчас `1.0.0-beta.1.26.51-stable`); у beta нет обещаний совместимости, сигнатуры могут поехать |
| Ключ `gametest` и раскладка `level.dat` | смена формата мира | перечитать NBT руками |
| `.mcstructure` `format_version: 1`, `version` в палитре | смена формата структур | пересобрать генератор |
| Поиск процесса через `cmdline` | смена образа/энтрипоинта | подправить `sendCommand()` |
| Разбор строк `onTestPassed:` / `onTestFailed:` / `Experiment(s) active:` | смена формата лога | подправить `analyzeLog()` |

Обычный прогон — **около 25 секунд**, включая сборку аддона. Мир каждый раз
создаётся заново: `scripts/bds-gametest.mjs` удаляет `worlds/gametest` перед
стартом, поэтому обе фазы (создать мир → пропатчить `level.dat` → поднять
снова) отрабатывают всегда, а не только на «холодном» запуске. Состояние между
прогонами не накапливается — это и делает результат воспроизводимым.

Дольше бывает ровно один раз: на самом первом запуске образ качает сам BDS в
`docker/bds/data/` — вот те самые 3–4 минуты. Дальше бинарник лежит локально.

Замер: удалили `docker/bds/data/worlds/gametest`, прогнали — 23 секунды,
`level.dat: Beta APIs experiment enabled (3010 -> 3022 bytes)`, оба теста
зелёные.

В `dist/bds-gametest.log` при этом видно один `Server started`, а не два:
контейнер между фазами пересоздаётся, и в файл попадает лог только второй
фазы. Считать по этой строке число стартов нельзя.

Новый сценарий — 20–30 строк рядом с существующими, отдельной инфраструктуры
не требует.

Главный риск не в объёме кода, а в том, что beta-модуль живёт отдельно от
стабильного `@minecraft/server` 2.10.0 и обновляется по своему календарю.
Поэтому лента проверок разделена: продукт собирается и проверяется на стабильном
API (`npm run bds:check`), а `npm run bds:gametest` — отдельный dev-прогон,
который можно уронить и починить, не трогая продукт.
