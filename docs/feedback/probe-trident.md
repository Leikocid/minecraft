## 1. Возврат вёдер (xasm33, L0-trdt-adrf, P1)

**Число.** Пробный рецепт ` G / BTB / G ` → токен на Крафтере:

| Случай | Сделано | Пустых вёдер у игрока / на земле / в сетке | Наполненных вёдер |
|---|---|---|---|
| вода, инвентарь свободен | токен 1 (у игрока) | 0 / 0 / 0 | 0 |
| вода, инвентарь полон (36 стопок земли) | токен 1 (на земле) | 0 / 0 / 0 | 0 |
| тот же рецепт с вёдрами молока (контроль) | токен 1 (у игрока) | 0 / 0 / 0 | 0 |
| ванильный торт (контроль) | торт 1 (у игрока) | **3** / 0 / 0 | 0 |

**Ответ.** Движок возвращает контейнеры для ванильного рецепта, но не для рецепта аддона. Вёдра нашего рецепта просто
исчезают: дубля нет, потеря есть. Молочный контроль показывает, что дело в рецепте аддона, а не в водяном ведре. Значит,
нужен свой код возврата 2 пустых вёдер. Это ветка «engine returns no bucket» из `L0-trdt-adrf`:
- `refund` перечисляет 2 ведра воды, `refundExchange` не нужен;
- успешный крафт получает 2 пустых ведра от скрипта, а при полном инвентаре они падают у ног.

**Как.**
- Сценарий `probe_trident_buckets`. Сетку Крафтера заполняет `replaceitem block … slot.container N`, крафт запускает
  импульс редстоуна. Через 40 тиков считаются инвентарь игрока и предметы на земле в радиусе 10.
- Что осталось в сетке, читается разрушением Крафтера: содержимое высыпается. Компонент `minecraft:inventory` у
  Крафтера скрипту недоступен (`readable from script: no`).

**Не измерено.** Верстак игрока, шифт-крафт и полный инвентарь в окне крафта. SimulatedPlayer окна крафта не открывает,
а Крафтер — другой путь кода. Ответ «вёдра не возвращаются» для верстака на iPad пока не проверен; см. «Что сервер не
измеряет».

## 2. Урон ванильного трезубца и Impaling (xasm34, P2)

**Число.** Survival SimulatedPlayer бьёт `attackEntity` по SimulatedPlayer-целям на 40 HP. Урон считан before- и
after-событием `entityHurt`, они совпали:

| Оружие | без брони, сухо | алмаз (броня 20, прочность 8), сухо | без брони, стоит в воде |
|---|---|---|---|
| `diamond_sword` (контроль) | 8.00 | 2.24 | 8.00 |
| `minecraft:trident` | **9.00** | **2.61** | 9.00 |
| `minecraft:trident` Impaling V | 9.00 | 2.61 | **21.00** |
| пробный предмет, `damage` 8, slot `spear` | **9.00** | **2.61** | 9.00 |
| пробный предмет Impaling V | 9.00 | 2.61 | **21.00** |

**Брошенный ванильный трезубец**, цель в 6 блоках, бросок после 20 тиков зарядки:
- без брони — **8.00** (оба броска);
- в алмазе — **2.24**.

Причина `projectile`, `damagingEntity` — игрок, `damagingProjectile` — `minecraft:thrown_trident`, `projectileHitEntity`
приходит с `source = player`.

**Утопленник** (`spawnWithoutBehaviors`, урон записан и отменён):

| Оружие | в воде | на суше |
|---|---|---|
| трезубец | 8.86 | 8.86 |
| трезубец Impaling V | **20.66** | 8.86 |
| пробный предмет | 8.86 | 8.86 |
| пробный предмет Impaling V | **20.66** | 8.86 |

**Ответ.**
- Ближний бой — 9, брошенный — 8. Пункт `xasm34` «expected 9/8» подтверждён замером.
- У кастомного предмета `minecraft:damage` 8 даёт 9.00 (+1 за руку), то есть «measured − 1» верно.
- Impaling: `canAddEnchantment` = true, и чара работает на кастомном предмете так же, как на ванильном: +12.00 по цели в
  воде (игрок и утопленник), 0 по сухой цели — утопленник на суше бонуса не получает. Дождь не проверялся.
- Слот чар трезубца в JSON предмета называется **`spear`**. Со значением `trident` предмет не разбирается вовсе:
  > `Failed to parse field ' -> components -> minecraft:enchantable -> slot: expected string to match the "none|all|g_armor|armor_head|armor_torso|armor_feet|armor_legs|sword|bow|spear|crossbow|melee_spear|g_tool|hoe|shears|flintsteel|shield|g_digging|axe|pickaxe|shovel|fishing_rod|carrot_stick|elytra|cosmetic_head" regex'`

  Строка из журнала прогона 19:18 UTC. Без компонентов предмет бил на 1.00. `L0-trdt` (строка про item JSON) называет
  слот `trident`, для TRDT-ITEM это `spear`.

**Как.** Сценарий `probe_trident_melee` и бросковая часть `probe_trident_throw`.
- Ближний бой: два удара на клетку с паузой 16 тиков, чтобы не попасть в окно неуязвимости.
- Мокрая клетка — источник воды на полу, огороженный камнем с четырёх сторон.

## 3. Жест: itemReleaseUse и isSneaking (P3)

**Число.** Пробный предмет (`use_modifiers` 3600 с), SimulatedPlayer: `useItemInSlot`, N тиков, `stopUsingItem`:

| Случай | События | `useDuration` при отпускании | `isSneaking` в обработчике |
|---|---|---|---|
| заряд 20, стоя | use, start (72000), release, stop | 71980 | false |
| заряд 20, присед на всём протяжении | то же | 71980 | **true** |
| заряд 20, присед снят в том же ходе скрипта, что и отпускание | то же | 71980 | **false** |
| заряд 5 | то же | 71995 | false |
| заряд 40 | то же | 71960 | false |
| предмет только с `use_modifiers` (без анимации и чар) | то же | 71980 | false |
| ванильный трезубец (контроль), присед | use, start (72000), release, stop (`dur=0`) | 71980 | true |

**Ответ.**
- `itemReleaseUse` у кастомного предмета без `throwable` приходит в 6 случаях из 6, вместе с `itemStopUse`.
- Заряд = 72000 − `useDuration`, в тиках, ровно (5 / 20 / 40). Для этого хватает одного `use_modifiers`.
- `isSneaking` в after-событии — живое значение на момент обработчика, а не на момент отпускания. Если присед снят в том
  же ходе, приходит false. Before-события отпускания в 2.10.0 нет: в `WorldBeforeEvents` есть `itemUse`, но нет
  `itemReleaseUse` (`awk '/^export class WorldBeforeEvents /,/^}/' node_modules/@minecraft/server/index.d.ts`).
- **Касание пальцем.** SimulatedPlayer читается как
  `lastInputModeUsed=KeyboardAndMouse touchOnlyAffectsHotbar=false platformType=Desktop`. Кнопка `Sneak` в
  `inputInfo.getButtonState` остаётся `Released`, даже когда `isSneaking=true`: прибор задаёт состояние, а не ввод.
  Серверу доступны три признака сенсора: `inputInfo.lastInputModeUsed` (`Touch`), `clientSystemInfo.platformType`
  (`Mobile`) и `inputInfo.getButtonState(Sneak)`. Как iPad-касание и переключатель приседа выглядят в этих событиях,
  показывает только устройство (TRDT-IPAD-01-AA).

**Как.** Сценарий `probe_trident_release`, подписки на `itemUse`, `itemStartUse`, `itemReleaseUse`, `itemStopUse`,
`itemCompleteUse`.

## 4. Рывок: Тягун III и калибровка applyKnockback (xasm37, P4)

**Число.** Ванильный трезубец с Тягуном III, заряд 20 тиков, игрок стоит на ровной каменной площадке (у игроков
Сопротивление V, чтобы приземления не мешали следующим запускам).

| Условие | Тангаж | Первый тик (гориз. / верт.) | Пик | Дальность приземления |
|---|---|---|---|---|
| сухо, ясное небо (контроль) | −30° | 0.000 / 0.000 | 0 | не взлетел |
| дождь над сухой землёй | 0° | 3.000 / 0.002 | 0 | скольжение 7.92 |
| дождь | −30° | 2.601 / 1.497 | +12.09 | **17.85** (+37 т) |
| дождь | −45° | 2.124 / 2.120 | +22.13 | **14.87** (+49 т) |
| дождь | −90° | 0 / 3.002 | **+39.77** | на месте (+66 т) |
| в воде (лунка в 1 блок) | −30° | 2.601 / 1.827 | +13.36 | 24.94 (старт на 1 ниже площадки) |
| в воде | −45° | 2.124 / 2.590 | +23.77 | 20.82 |
| в воде | −90° | 0 / 3.670 | +41.90 | на месте (+67 т) |

**`applyKnockback` на стоящем игроке**, первый тик:
- `{x:1}` → 0.400 б/т, `{x:2}` → 0.800 — линейно;
- вертикаль 0.5 → 0.500, 1 → 1.000.

**Калибровка.**
- Тягун III даёт 3.00 б/т вдоль взгляда (`|d| = 3.00` при любом тангаже под дождём).
- Отсюда **H = 3.00 / 0.400 = 7.50**, **V = 3.00 / 1.000 = 3.00** для `applyKnockback({x: v.x·H, z: v.z·H}, v.y·V)`.
- В воде вертикаль сильнее: V по воде = 3.67.

Проверка — скриптовый рывок с H 7.50, V 3.00 в сухом воздухе:

| Тангаж | Пик | Приземление | против Тягуна под дождём | против Тягуна в воде (пик) |
|---|---|---|---|---|
| −30° | +12.08 | 17.85 | **1.00×** пик, 1.00× дальность | 0.90× |
| −45° | +22.13 | 14.87 | **1.00×**, 1.00× | 0.93× |
| −90° | +39.78 | — | **1.00×** | 0.95× |
| 0° (по земле) | 0 | скольжение 6.61 | 0.83× | — |

**Ответ.**
- Рывок `applyKnockback` с H 7.5, V 3.0 повторяет запуск Тягуна III с ровной земли под дождём один в один. Это в пределах
  ±20 % из `xasm37`.
- Отклонения два:
  - скольжение по земле при взгляде строго горизонтально — 0.83×;
  - из воды ванильный Тягун подкидывает выше — рывок даёт 0.90–0.95× его пика.
- Без воды и дождя ванильный Тягун не срабатывает вовсе (контроль 0.00).

**Как.** Сценарий `probe_trident_riptide` на своей каменной площадке в 1600 блоках от теста.
- Погода `setWeather(Rain)`, 100 тиков ожидания.
- Направление взгляда ставится `lookAtLocation`: тангаж из `teleport({rotation})` у SimulatedPlayer до головы не доходит.
- Отклонение взгляда от заданного ≤ 0.002.

## 5. Отмена урона от приземления (xasm36, P5)

## 9. Висящий снаряд после перезапуска (P9)

**Число.** Перед остановкой сервера seed оставляет 4 тела в загруженной ticking area `andrew_gt_trdt_rs`:
- R — тело возврата, висит в воздухе;
- F — свой снаряд в полёте;
- G — свой снаряд, воткнутый в пол;
- V — ванильный `thrown_trident` в полёте, брошенный SimulatedPlayer.

Летящие тела до самой остановки подбрасывает интервал, чтобы сохранение застало их в воздухе. Каждое несёт
`andrew:tr.throw`. В цитируемом прогоне от записи seed до проверки прошло 10.24 с.

| Тело | `world.getEntity(старый id)` | id после | `andrew:tr.throw` | `entityLoad` | При загрузке | Дальше |
|---|---|---|---|---|---|---|
| R | найдено | тот же | `probe-R` | да, на старте | на месте, скорость 0 | висит, сдвиг 0.00 |
| F | найдено | тот же | `probe-F` | да | в воздухе: y +14.28…+15.96, vy −0.794…−0.977 | долетел до пола (y 1.00) |
| G | найдено | тот же | `probe-G` | да | в полу, скорость 0 | на месте |
| V | найдено | тот же | `probe-V` | да | в воздухе: y +14.03…+15.89, vy −0.886…−1.067 | долетел до пола |

Положения при загрузке — диапазон по прогонам 19:24–19:47 UTC (F — четыре, V — три): где тело застала остановка,
зависит от её момента.
`entityLoad` пришёл для всех четырёх за 20–32 тика до начала проверки, то есть при старте мира, ещё до первой команды.
Тел этих типов без записанного ключа в загруженном мире — 0.

**Ответ.**
- Перезапуск ничего не теряет: тело и снаряды остаются с тем же `Entity.id` и тем же динамическим свойством.
- Скрипт видит их в `entityLoad` при загрузке чанка.
- Снаряд, застигнутый в полёте, продолжает полёт с сохранённой скоростью и падает. Тело без физики висит, где висело.
- Для `L0-trdt-ecus`: запись по `throwId` найдёт свою сущность. Тело без записи надо убирать в `entityLoad` — сами они не
  исчезают.

**Как.** Сценарии `probe_trident_restart_seed` и `probe_trident_restart_check`, перезапуск — `RESTART_AFTER` в
`scripts/bds-gametest.mjs`.

## P10. Источник урона снаряда, запущенного скриптом (L0-trdt-cons P10, addm §3)

**Число.** Свой снаряд с `impact_damage` 8 и `owner` = бросивший, `shoot()` со скоростью ванильного броска, цель без
брони в 6 блоках. Два выстрела на рантайм:

| Рантайм | Урон | `damagingEntity` / `damagingProjectile` | `projectileHitEntity` |
|---|---|---|---|
| `minecraft:snowball` | **нет события урона** | — | есть, `source = player` |
| `minecraft:thrown_trident` | **8.00** (`projectile`) | игрок / `andrew:probe_trident_thrown_tr` | есть |
| `minecraft:arrow` | **8.00** (`projectile`) | игрок / `andrew:probe_trident_thrown_ar` | есть |

Без `stop_on_hit` все три пролетают цель насквозь и втыкаются в землю в 5.30–7.50 блока за ней (по четырём прогонам).

**Ответ.** Снаряд на snowball-рантайме — рантайм из `L0-adr-twth` — собственного урона не наносит, хотя событие попадания
приходит. Ванильные 8 HP броска даёт рантайм `thrown_trident` или `arrow`: с правильным источником, его поднимет
before-событие. Остаётся путь «урон скриптом по `projectileHitEntity`» (`addm` §3). Чем ещё рантаймы `thrown_trident` и
`arrow` отличаются (подбор, Верность, звук), здесь не мерилось.

## Что недостижимо стабильным API

| Что | Замер | Пункт спеки | Чем закрывается |
|---|---|---|---|
| Призвать ванильный брошенный трезубец скриптом | `spawnEntity("minecraft:thrown_trident")` → `InvalidArgumentError … is not summonable` (P9) | §02 бросок и возвращение: ванильную Верность не переиспользовать | свой снаряд и своё тело возврата (`L0-adr-twth`) |

| Тягун без воды и дождя средствами ванили | ванильный Тягун III на сухой земле при ясном небе: 0.00 (P4) | §02 Тягун в воздухе и в любых измерениях | скриптовый рывок `applyKnockback`, H 7.5, V 3.0 |
| Узнать в момент отпускания, держал ли игрок присед | before-события отпускания нет; `isSneaking` в `itemReleaseUse` — живое значение, снятый в том же ходе присед читается как false (P3) | §02 «отдельная кнопка не требуется»: бросок и рывок на одном жесте (`xcx28`) | решение по `isSneaking` в обработчике; граничный случай (присед отпущен одновременно с кнопкой) уходит в бросок |

Две развилки — ограничения рантайма, а не API: их можно обойти выбором рантайма.
- Собственный урон снаряда на snowball-рантайме — 0 (P10). Обход — рантайм `thrown_trident` или `arrow`, либо урон скриптом.
- Скрипт не читает сетку Крафтера (компонента `minecraft:inventory` нет). Это ограничение прибора, а не спеки.

## Что сервер не измеряет (нужен iPad — TRDT-IPAD-01-AA)

- **Касание пальцем и переключатель приседа** (§02, жест). SimulatedPlayer — `KeyboardAndMouse` / `Desktop`, кнопка
  `Sneak` всегда `Released`. Приходит ли с iPad `itemReleaseUse` после долгого касания и читается ли `isSneaking` при
  включённом приседе, видно только на устройстве. На сервере это различат `inputInfo.lastInputModeUsed`,
  `clientSystemInfo.platformType` и `inputInfo.getButtonState(Sneak)`.
- **Верстак игрока, шифт-крафт, полный инвентарь в окне крафта** (§01, приёмка §03 «рецепт и возврат 2 вёдер»).
  SimulatedPlayer окна крафта не открывает, замер 1 — Крафтер.
- **Вид**: поза кручения Тягуна, видимость летящего и возвращающегося трезубца. `Entity.playAnimation` в 2.10.0 есть,
  но существует ли ванильная анимация кручения игрока и как она выглядит, сервер не скажет.
