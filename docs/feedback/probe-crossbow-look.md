# Пробы под вид Скалкового арбалета — SCLKUI-PROBE-01-AA

Что движок разрешает показать у кастомного предмета с `minecraft:shooter`. Отсюда видно, какие пункты письма Андрея
от 06.10 выполнимы, а какие нет: текстура в нашем цвете, анимация зарядки в руке и в инвентаре, вид заряженного
арбалета. Продуктовый пак не тронут.

- **Стенд.** BDS 1.26.51.1, `@minecraft/server` 2.10.0, приватный инстанс `dist/bds-lookp` (`andrew-bds-lookp`,
  порты 19936 / 19960–19969 / 7891), к нему никто не подключался. Прогоны 2026-10-06:
  - 19:39 UTC — первый;
  - 19:42 UTC — с контролями контент-лога;
  - 19:46 UTC — финальный, артефакт `.ai/verify/SCLKUI-PROBE-01-AA/3.json`, exit 0, 6/6 RESULT.

  Числа ниже взяты из финального прогона. Где они есть в двух других, они совпали до цифры.
- **Чего нет.** На Mac нет клиента Bedrock, а BDS ничего не рисует. Поэтому всё, что про картинку на экране,
  измерено со стороны сервера, а глазами закрывается только на iPad. Для этого собран набор
  `dist/look-probe-kit.mcaddon` (раздел «Проверка на iPad»). Где ответ держится на документации, а не на замере,
  так и написано.
- **Где пробы.** Всё в `packs/gametest/look-probe/`, и в обычном прогоне ничего из этого не работает:
  - `run.sh` — прогон на BDS. На время одного прогона он ставит сценарии (`probe.ts`), пробные предметы
    (`items/`, `items-control/`) и Molang-считыватель, а на выходе всё снимает;
  - `player-molang.mjs` — считыватель. Это ванильный `player.json` из архива самого BDS (в репозиторий не кладётся,
    это файл Mojang) плюс по одному контроллеру анимации на каждый бит каждого запроса. Скрипт собирает значение
    из тегов игрока;
  - `kit.mjs` — набор для iPad. Все картинки рисует сам скрипт, текстур Mojang в наборе нет.

  В релизный архив ничего из этого не попадает (критерий 2, артефакт `2.json`).

## Q1. `minecraft:icon`: больше одной текстуры по состоянию — нет

| Замер (формат 1.21.90) | Результат |
|---|---|
| `andrew:probe_look_icon_keys`: `textures` = `default`, `pulling_0`, `pulling`, `charged`, `arrow` | предмет зарегистрирован, в контент-логе **0 строк** |
| Контроль: `textures` без `default` | `[Components] andrew:probe_look_ctl_nodefault : minecraft:icon component should include default key in textures map to set icon texture` |
| Контроль: `max_stack_size: "lots"` | `[Item] Error Parsing Item … invalid numeric value` |
| Контроль: несуществующий компонент `minecraft:andrew_no_such_component` | **0 строк**: неизвестный компонент лог не ловит |
| `minecraft:icon_variant: {}` (строка есть в бинарнике) | 0 строк, то есть как у несуществующего компонента. Признаков, что он что-то делает, нет |

- Карта `textures` принимает любые ключи молча, но парсер её проверяет: без `default` выдаёт ошибку. Значит,
  молчание про `pulling`/`charged` — это «принято», а не «не читалось».
- Какие ключи движок читает, видно по строкам `bedrock_server-1.26.51.1`:
  - иконка — `NetworkedItemComponent<IconItemComponent>`, то есть сервер передаёт её клиенту;
  - в коде рядом сравниваются только литералы `default` и `dyed`;
  - `pulling`, `charged`, `icon_trim` — 0 вхождений.
- Документация (поиск изолированным агентом, файлов не скачивали):
  - Microsoft Learn, `minecraft:icon`: только `default`;
  - Bedrock Wiki: `default`, `dyed`, `icon_trim`, `bundle_open_back`, `bundle_open_front`.

  Ни одного ключа про натяжение или заряд нет.
- Ванильный арбалет. В `item_texture.json` из `Mojang/bedrock-samples` есть массив `crossbow_pulling`, но ничто в
  данных не выбирает из него значок. Смена значка ванильного арбалета зашита в клиент по идентификатору. Это вывод
  из отсутствия механизма, прямо так нигде не написано.
- Чего сервер не исключает: клиент может читать ключи, которых нет в серверном коде (так устроены `icon_trim` и
  `bundle_open_*`). Поэтому `pulling`/`charged` проверяются ещё и на iPad, предметом «icon state keys». Ожидание —
  значок остаётся «R».

## Q2. Attachable на кастомном предмете в руке — да, по документации; глазами — набор

- Microsoft Learn, Attachables: идентификатор attachable «must match an identifier for an existing item in the
  game or your resource pack». Пример там на кастомном `demo:wrench`. Attachable задаёт вид предмета в руке и на
  теле. На значок в инвентаре он не влияет: ни в одном источнике такого нет.
- Сервер attachable не загружает: это клиентская часть RP, в бинарнике BDS только описание
  `query.equipped_item_is_attachable`. Со стороны сервера измерено одно: Molang, которым такой attachable
  анимируется, у нашего предмета живой (Q3).
- В наборе собран простейший attachable на `andrew:probe_look_shooter`:
  - своя геометрия: ложе, дуга и шесть столбиков;
  - одна анимация `readout`, она масштабирует столбики значениями запросов;
  - привязка к руке через `q.item_slot_to_bone_name(c.item_slot)`;
  - render controller меняет окраску: серая в покое, жёлтая при натяжении, бирюзовая, если клиент сочтёт предмет
    заряженным.

## Q3. Molang-запросы натяжения у кастомного shooter

Считывание на сервере, тем же игроком и тем же предметом:
- `player.json` из `vanilla_1.26.30` плюс 464 контроллера-бита по 16 запросам, точность 1/1024;
- контроли расшифровываются точно: константы 1234.5 и −3.25, `query.health` = 20 в каждом прогоне;
- значение отстаёт на ≤ 1 тик (теги ставятся командами контроллеров).

Продуктовый `andrew:sculk_crossbow` и пробный `probe_look_shooter` дали одинаковые числа на каждом тике.
`max_draw_duration` и `use_duration` = 1.25 с, заряд — `complete@+25`.

| Запрос (продуктовый арбалет) | Покой | Середина натяжения (+12 т) | После заряда (+42 т) |
|---|---|---|---|
| **`query.main_hand_item_use_duration`** | **0** | **13** — оставшиеся тики: 24 на +1 … 1 на +24, 0 с +25 | **0** |
| **`query.item_remaining_use_duration`** | **0** | **0.649** — оставшиеся секунды: 1.199 → 0.05 | **0** |
| `query.item_remaining_use_duration('main_hand', 1.0)` | 0 | 0.52 — от 0.96 вниз до 0.039 | 0 |
| **`query.item_max_use_duration`** | **500** | **500** | **500** — константа, тики × 20 |
| `query.main_hand_item_max_duration` | 25 | 25 | 25 — константа и в покое |
| `query.item_in_use_duration` | 500 | 240 — прошедшие тики × 20 | 500 |
| `query.is_using_item` | 0 | 1 | 0 |
| `query.item_is_charged`, `('main_hand')`, `(0)` | 0 | 0 | **0** |
| `query.is_charged`, `query.is_charging` | 0 | 0 | 0 |
| `query.get_animation_frame` | 0 | 0 | **0** |

Контроли:
- **Ванильный арбалет** даёт те же числа по всем строкам, кроме одной: `get_animation_frame` = **4** после заряда
  (кадр «со стрелой»), с +25. У нашего предмета там **0**.
- `item_is_charged` даёт 0 и у заряженного ванильного арбалета, который на следующем нажатии выстрелил. Значит,
  на сервере этот запрос ничего не решает: что он вернёт на клиенте, покажет только iPad.
- **Ванильный лук:**
  - `main_hand_item_use_duration` = 71988 на +12 (72000 − 12);
  - `item_remaining_use_duration` = 3599.399 с;
  - `item_max_use_duration` = 72000 × 20. Считыватель сворачивает это значение по 2^18 и показывает 129 280;
  - `get_animation_frame` = 1 всё натяжение.

Что из этого следует для анимации:
- **Натяжение видно.** Прогресс 0→1 = `1 - q.main_hand_item_use_duration / q.main_hand_item_max_duration` при
  `q.main_hand_item_use_duration > 0`, или `1 - q.item_remaining_use_duration('main_hand', 1.0)`. Ванильные
  attachable лука и арбалета в `bedrock-samples` строят натяжение на той же паре: `main_hand_item_max_duration` и
  `main_hand_item_use_duration`.
- **«Заряжен» не виден.** После заряда все три запроса возвращаются к значениям покоя. Признака заряда у нашего
  предмета на сервере нет ни в одном из 16 запросов, а у ванильного он есть (`get_animation_frame` = 4).
- **Нажатие-выстрел тоже открывает сессию использования.** У нашего предмета это `start@+0 … release@+1`, у
  ванильного арбалета только `use@+0`. Анимация, завязанная на `main_hand_item_use_duration`, будет мелькать и на
  время нажатия, которым стреляют.
- Это серверная оценка. В attachable запросы относятся к держателю, но тот ли ответ даст клиент, видно только на
  iPad: столбики в наборе.

## Q4. Значок в инвентаре по состоянию предмета

**Сам по себе — нет.**
- Ключей по состоянию нет (Q1).
- Attachable значок не трогает (Q2).
- Значок задаётся компонентом типа предмета и передаётся клиенту целиком. Molang у значка нет.

**Скриптом — да, но только одна вторая картинка.** У `minecraft:dyeable` значок окрашенного предмета берётся из
ключа `dyed` вместо `default` (Bedrock Wiki: «Once dyed, the item will display the `dyed` icon texture rather than
`default`»). Цвет хранится в экземпляре, и стабильный 2.10.0 даёт его записать: `ItemDyeableComponent.color`.

| Замер на BDS (`probe_look_shooter` = форма продукта + `dyeable`) | Результат |
|---|---|
| Новый экземпляр | компонент есть, `color` undefined, `defaultColor` undefined |
| A. Контроль: зарядить и нажать | `complete@+25`, на нажатии стрела (1) |
| B. Записать цвет **заряженному**, потом нажать | цвет читается 1,1,1; **стрела вылетела (1)**: заряд не потерян |
| C. Записать цвет **посреди натяжения** (+12) | натяжение не прервалось: `complete@+25`, на нажатии стрела (1) |
| F. Новый оттенок **на каждом тике натяжения** (26 записей) | `complete@+25`, на нажатии стрела (1) |
| D. Снять цвет (`color = undefined`) | читается undefined |
| E. Правило набора: окрасить в тик заряда, снять на нажатии-выстреле, два круга | оба круга: заряд → окрашен, нажатие → стрела (1) и цвет снят, следующий заряд в норме |

Что даёт этот путь:
- **«Заряжен» в инвентаре выполним.** Значок `dyed` держится, пока арбалет заряжен.
- **Кадров натяжения не будет.** Во время натяжения меняется только оттенок картинки `dyed`: по Wiki она серая и
  тонируется цветом. Кадры натяжения, как у ванильного, этим не сделать.
- **Цена.** Окрашиваемый предмет можно покрасить и отмыть в котле, так что состояние надо пересинхронизировать
  скриптом. Будет ли клиент рисовать `dyed`, видно только на iPad: предметы «look shooter» и «plain».

## Q5. `flipbook_textures.json` на значок предмета — нет

- По документации `atlas_tile` — это ключ из `terrain_texture.json`, то есть атлас блоков (Bedrock Wiki, Flipbook
  Textures; на Microsoft Learn пример только на блоке). Для `item_texture.json` ничего не документировано.
- У сервера этой подсистемы нет: в бинарнике BDS 0 строк `flipbook`. Замерить её можно только на клиенте.
- Если клиент всё-таки оживит значок предмета, частоту задаёт `ticks_per_frame`: в наборе 10 тиков = 2 кадра в
  секунду, у поля нет документированного значения по умолчанию. У записи нет поля, которое ссылалось бы на
  предмет, его состояние или Molang, поэтому анимация идёт по кругу одинаково в покое, при натяжении и заряженной.
  Для анимации зарядки flipbook не годится ни в каком случае.

## Что следует для трёх пунктов Андрея

| Пункт | Выполнимо? | На чём стоит |
|---|---|---|
| 1. Текстура арбалета в нашем цвете | **Да, полностью** | значок — свой PNG под `default` (`andrew_sculk_crossbow`). Без attachable та же картинка в руке плоским спрайтом, с attachable — своя раскраска модели. Текстуры Mojang не нужны |
| 2а. Анимация зарядки **в руке** | **Да** | attachable (Q2) + `main_hand_item_use_duration` / `main_hand_item_max_duration` (Q3). Числа сняты на сервере, на клиенте подтверждает iPad |
| 2б. Анимация зарядки **в инвентаре** | **Нет** | ни значок, ни flipbook, ни attachable от натяжения не зависят (Q1, Q4, Q5). Максимум — оттенок второй картинки по ходу натяжения (Q4, F) |
| 3а. Вид заряженного **в инвентаре** | **Да, скриптом** | `dyeable` + `dyed`: заряд не теряется, правило E прошло два круга (Q4). Что значок меняется, подтверждает iPad |
| 3б. Вид заряженного **в руке** | **Без attachable — да** (спрайт берёт значок `dyed`, если клиент так рисует: iPad). **С attachable — не доказано** | признака заряда для нашего id на сервере нет: `item_is_charged` 0, `get_animation_frame` 0 против 4 у ванильного (Q3). Если на iPad красный и оранжевый столбики не появятся, attachable заряд показать не может |

Развилка для 2а и 3б. Сразу и анимация натяжения в руке (attachable), и вид заряженного в руке требуют одного из
двух:
- клиентского признака заряда, если iPad его покажет;
- **отдельного id для заряженного состояния.** Скрипт подменяет предмет, и выстрел тогда идёт скриптом, а не
  нативным зарядом. Это переделка пути выстрела, она не мерялась.

Без этого остаётся выбор: анимация натяжения (attachable) **или** заряженная картинка в руке (спрайт `dyed`).

## Технически невыполнимо

- **Анимация зарядки в инвентаре кадрами, как у ванильного арбалета.** Значок кастомного предмета не меняется по
  ходу натяжения:
  - в `minecraft:icon` нет ключей по состоянию (Q1);
  - flipbook документирован только для блоков и не зависит от состояния (Q5);
  - attachable значок не трогает (Q2);
  - `dyed` даёт одну вторую картинку и её оттенок (Q4).
- **Ванильная поза рук с заряженным арбалетом у нашего предмета.** В `bedrock-samples` анимации игрока выбирают её
  по `query.get_equipped_item_name == 'crossbow'`, и под `andrew:sculk_crossbow` это не подходит. Чтобы это
  изменить, надо переопределять клиентский `player.entity.json` — файл Mojang, который ломается с обновлениями.
  Это не мерялось, вывод из сэмплов.
- **Вид заряженного в руке поверх attachable** пока не доказан выполнимым (3б): решит iPad.

## Проверка на iPad

Сборка: `node packs/gametest/look-probe/kit.mjs` → `dist/look-probe-kit.mcaddon`. В архиве два пака:
- `Andrew look probe BP` — четыре предмета и скрипт на стабильном API;
- `Andrew look probe RP`.

Экспериментальные функции не нужны. Порядок:
1. Импортировать архив, создать новый мир (Творческий), включить `Andrew look probe BP`, RP подтянется сам.
2. В инвентаре творчества найти по слову «Probe» четыре предмета, взять стрелы и ванильный арбалет для сравнения.
3. Смотреть в первом и третьем лице. Вид меняется в настройках, раздел «Видео» → перспектива камеры.

| Предмет | Что сделать | Что записать |
|---|---|---|
| **Probe: look shooter** (Q2, Q3) | держать, натянуть до заряда, выстрелить | 1) в руке модель из брусков, а не плоская «R»? 2) какие столбики растут при натяжении и какие стоят после заряда. Слева направо: красный — `item_is_charged`, оранжевый — `get_animation_frame`/5, зелёный — `is_using_item`, синий — `main_hand_item_use_duration`/25, фиолетовый — `item_remaining_use_duration` нормированный, белый — `item_max_use_duration`/500. 3) окраска модели: серая / жёлтая / бирюзовая |
| **Probe: look shooter** и **Probe: plain dyeable shooter** (Q4) | зарядить, посмотреть хотбар, выстрелить | значок «R» сменился на «D», пока заряжен, и вернулся после выстрела? У «plain» (без attachable) то же видно и в руке? |
| **Probe: icon state keys** (Q1) | натянуть и зарядить | значок в хотбаре и в руке остался «R» или менялся на «P»/«C» |
| **Probe: flipbook icon** (Q5) | просто держать в хотбаре | меняются ли цифры 1→2→3→4 дважды в секунду, или стоит одна картинка (или сжатая полоса из четырёх) |

## Сопутствующее (измерено)

- После выстрела SimulatedPlayer не может начать новое использование ~9 тиков. Нажатие через 4 тика после
  выстрела отказывало 5 раз подряд и прошло на шестой попытке (`startedOnTry=6` во всех кругах B–F). После заряда
  без выстрела отказа нет (`startedOnTry=1`).
- Подмена стрелы на болт в продукте работает и под считывателем: на нажатии `bolt@+0`.
