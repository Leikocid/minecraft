# Зонд движка strf-p006 — результаты

Ответы на 11 вопросов зонда `L0-strf-p006` о структурах на **BDS 1.26.51.1** со стабильным `@minecraft/server` **2.10.0**, плюс отдельные находки о движке. Все числа взяты из одного полного прогона
`npm test && npm run bds:check && npm run bds:gametest` от 2026-09-26 (код `7a5b2ee`, exit 0; npm test 300/300, bds:check selftest 17/17 в обоих запусках, bds:gametest 43/43).
Этот прогон доказывает артефакт `.ai/verify/PRB-REPORT-01-AA/6.json`. Строки `RESULT` ниже переписаны из полного лога BDS, потому что в артефакте хранится только хвост вывода.

**Вывод для оператора.** Все четыре структуры можно делать так, как написано в спеке и ADR. Ни один вопрос не изменил схему: блок-сущности переживают `place` (Q1), а ванильные таблицы лута работают через `/loot insert` (Q4). Есть три поправки к реализации, и схему они не меняют. `fillBlocks` за один вызов берёт не больше 32 768 клеток, поэтому расчистку режем на куски. Вылеченный житель сохраняет имя: спека это допускает. Защиту `nameTag` от исчезновения по расстоянию зонд не доказал: она остаётся предположением, и приёмочный тест Мельницы должен проверить её с игроком.

## Пункты подробно

«Измерено» — что напечатал движок в этом прогоне. «Не измерено / предположение» — то, на что ответ опирается, но чего зонд не проверял.

### Q1 — `place` сохраняет блок-сущности · PASS

- Измерено: оба сундука после `place` остались `minecraft:chest` с инвентарём (27 слотов, пустые). Спавнер остался `minecraft:mob_spawner` и выдал `minecraft:zombie` через **40 тиков (2 с)**. В контрольной коробке без спавнера мобов не было. Предыдущий прогон PRB-PLACE-01-AA дал 3 с.
- `[probe] Q1 RESULT PASS — both chests are chests with an Inventory, the spawner is a mob_spawner and spawned minecraft:zombie in 2 s`
- Следствие: `EntityIdentifier` из `.mcstructure` работает, и запасной путь ADR-strf-02 (скриптовый псевдо-спавнер) не нужен.

### Q2 — поворот · PASS

- Измерено: для поворотов 0/90/180/270 позиции сундуков, спавнера, визгуна, двери и ступени совпали с `rotateLocal`. Состояния повернулись: у сундуков `cardinal_direction` south→west→north→east; у двери `direction` 0→1→2→3; `weirdo_direction` у ступени 3→0→2→1. `can_summon=true` сохранился во всех четырёх. Размер AABB 9×5×7 ↔ 7×5×9, и `location` каждый раз остаётся минимальным углом.
- `[probe] Q2 RESULT PASS — rotateLocal vs placement: 0:ok 90:ok 180:ok 270:ok`
- `[probe] Q2 origin RESULT PASS — location is the min corner of the rotated AABB at 0/90/180/270: true`

### Q3 — визгун из шаблона вызывает Хранителя · PASS

- Измерено: визги на тиках 4/204/404/604. Со второго визга у игрока появляется `darkness`. Хранитель появился на тике **694**, через 90 тиков после 4-го визга. После прогона `can_summon=true`.
- `[probe] Q3 RESULT PASS — a Warden appeared 694 tick(s) in, after 4 shriek(s); stages A (doMobSpawning as the GameTest world has it); shriek ticks=[4 204 404 604]; darkness on the player at 3 shriek(s) (darkness = the shriek counted as a warning); can_summon after the run=true`

### Q4 — ванильные таблицы лута · PASS (новое измерение)

- Первый прогон PRB-LOOT-01-AA заключил FAIL, и это было **ложное отрицание**. Зонд читал сундук по координатам относительно тестовой площадки, а `/loot insert` заполнял блок по мировым координатам. Этот вывод отозван (коммит `e411e3a`). Предложение перевести Город Хранителя и Бастион на нашу взвешенную таблицу **не принимается**.
- Измерено заново: движок принимает написание `loot "chests/<id>"` — голый id в кавычках, без `loot_tables/` и без `.json`. Каждая таблица дважды дала разное ванильное содержимое, значит таблица разыгрывается, а не кладётся заглушка:
  - `chests/ancient_city` (все 10 сундуков Мини-города Хранителя): PASS. Например, №1 = уголь×8, компас, алмазные поножи, `disc_fragment_5`, эхо-осколок×2, зачарованная книга, железные поножи, `sculk_catalyst`×2.
  - `chests/bastion_treasure` (3 центральных сундука Мини-Бастиона): PASS, в обоих вызовах есть `netherite_ingot` и `netherite_upgrade_smithing_template`.
  - `chests/bastion_other` (7 внешних сундуков): PASS.
  - Контроль `chests/simple_dungeon`: PASS.
  - Полный сундук: `successCount=1`, но содержимое **не изменилось** и на землю выпало **0** предметов. Значит `successCount` не доказывает заполнение: заполнение проверяют по содержимому контейнера.
- Игрок для команды не нужен: SimulatedPlayer в этих тестах не создаётся.

### Q5 — неисчезающие мобы при разгрузке и рестарте · PASS (частично)

Прогон — `npm run bds:check`, два запуска BDS на одном сохранённом мире. Строка результата дословно:

> `probe Q5 RESULT PASS — 10/10 named zombie villagers survived unload + restart with their names; control (tag, no nameTag) 10/10 — nothing despawns with no player online, so this proves persistence across unload + restart, not nameTag vs distance despawn`

- Измерено: из 10 именованных зомби-жителей **выжили 10**, и **10 сохранили имена**. Их разгружали снятием ticking area (чанк разгрузился за 1 тик, сущности пропали из `getEntities` через 5 тиков), потом перезапускали сервер. Контрольная группа (тег есть, имени нет) — тоже **10/10**. Перед повторной загрузкой чанк был не загружен, и видимых сущностей было 0. После загрузки (10 тиков) число сущностей устоялось за 45 тиков.
- **Оговорка важнее числа:** на сервере нет игрока, а без игрока онлайн ничто не исчезает. Поэтому доказана сохранность через разгрузку и перезапуск, а **не** то, что `nameTag` защищает от исчезновения по расстоянию.
- **Не измерено:** уход игрока на 2 км. На неигровом BDS его воспроизвести нельзя. То, что имя защищает от исчезновения по расстоянию, остаётся предположением: это известное поведение Bedrock, но здесь оно не проверено. Его закрывает приёмочный тест тела Мельницы с игроком. Если он провалится, запасной путь уже описан в выводе зонда: вести в динамическом свойстве мира список id стражей и досоздавать недостающих при загрузке чанка структуры.

### Q6 — бесконечная огнестойкость · PASS

- Солнце, измерено: `effect … infinite 0 true` через `runCommand` дал `fire_resistance amp=0 duration=-1`. В полдень (время 6000, свет неба 15) защищённый зомби-житель остался на **20→20** ОЗ, огня **0/300** тиков. Контрольный — **19→4** ОЗ, горел 299/300 тиков.
  - `[probe] Q6 RESULT sun: PASS — infinite fire_resistance kept the guarded zombie villager at full health at noon; visible fire on the guarded mob: NO, minecraft:onfire never present (server-side flag; what the client draws is confirmed on the iPad)`
  - Видимый огонь проверен только по серверному флагу `minecraft:onfire`. Что рисует клиент, видно только на iPad.
- Рестарт, измерено в `bds:check`:
  > `probe Q6 RESULT restart: fire_resistance present on 20/20 after unload + restart (minecraft:fire_resistance amp=0 duration=-1) — PASS, the infinite effect persists`
- Лечение, измерено: вылеченный через ~3840 тиков `minecraft:villager_v2` **сохранил имя**, но **потерял** `fire_resistance` и тег.
  - Зонд напечатал это как `Q6 RESULT cure: FAIL` и предложил вернуть эффект и тег. **Это расходится со спекой, и запасной путь зонда не принимается.** Правило `L0-wind-r005` и AC-wind-08 (§4.5, §9.9) требуют, чтобы вылеченный житель стал обычным: без тега `andrew:guard:*` и без эффекта от структуры. Движок делает это сам. Сохранённое имя спека допускает (`L0-wind-r005`, `L0-strf-r009`). Снимать его необязательно, и если снимать, это пишется как отклонение.

### Q7 — стоимость `place` и `getBlock` · PASS

- Измерено: `place` шаблона **35×30×35** (36 750 клеток) — **38 мс**, когда меняется каждая клетка (поверх камня), и **23 мс** без изменений (поверх того же шаблона). 64 `getBlock` — **0,560 мс** в среднем по 100 кругам, первый круг 1 мс. Сборка шаблона в памяти (`createEmpty`) заняла 68 мс. Предыдущий прогон PRB-PLACE-01-AA дал 39/24 мс и 0,550 мс.
- `[probe] Q7 RESULT place 35,30,35 = 38 ms (every cell changes), 23 ms (no change); 64 getBlock = 0.560 ms mean, 1 ms first round`
- Вывод: один `place` Мельницы укладывается в тик (50 мс), но запас небольшой. В том же тике не должно идти другой тяжёлой работы.

### Q8 — бюджет динамических свойств · PASS

- Измерено, один ключ: принято **32 767** ASCII-символов, 32 768 отвергнуто. Кириллических «ж» принято **16 383**, 16 384 отвергнуто. Предел считается в **байтах UTF-8**: 32 767 байт на строку. Ошибка: `ArgumentOutOfBoundsError … String length for dynamic property … Argument max: 32767`. Полная запись на ключ в 32 767 символов прибавила 32 784 байта.
- Измерено, всего: **1024 ключа по 32 767 символов = 33 574 826 байт (32,02 МиБ)** записались за 1506 мс **без ошибки и без предупреждения движка**: в логе нет строк про dynamic property, кроме строк зонда. Потолка до 32 МиБ нет. После очистки осталось 109 байт (как до теста).
- `[probe] Q8 RESULT one key: 32767 ASCII chars / 16383 'ж' chars; total walk: 1024 key(s) of 32767 chars = 33574826 bytes`
- Не измерено: переживает ли 32 МиБ динамических свойств рестарт и сколько стоит сохранение мира. Для ADR реестра это неважно: регион 32×32 чанка — это битсет на 128 байт плюс компактные записи экземпляров, на порядки меньше предела ключа.
- Предыдущий прогон PRB-CHUNK-01-AA эти числа напечатал, но в хвост артефакта они не попали. Здесь они сняты заново.

### Q9 — обнаружение загрузки чанка · PASS

- Измерено: `dimension.isChunkLoaded` **есть** в 2.10.0. Перебор прототипа `Dimension` дал 34 члена, из них про чанки/загрузку только `isChunkLoaded`, и это `function`.
- В незагруженном чанке `getBlock` возвращает **`undefined`**, а `getTopmostBlock` и `setBlockType` **бросают** `LocationInUnloadedChunkError`. Проверено на view-distance + 5 (37 чанков), на измеренной границе + 5 (9 чанков) и в 10 000 блоках.
- Расхождений `isChunkLoaded` с `getBlock` — **0** (в обоих прогонах).
- Вокруг SimulatedPlayer загружено **4 чанка** по +x. В мире без игрока (bds:check) не загружено **ничего**, спавн тоже.
- Вывод для валидации (ADR strc, шаг 3): сначала `isChunkLoaded`, потом `getTopmostBlock`. Иначе будет исключение, а не `undefined`.

### Q10 — `fillBlocks` воздухом · FAIL (для 40×30×40 одним вызовом) → нарезка

- Измерено: через границы чанков одним вызовом **работает**. 32×32×32 = 32 768 клеток на 9 чанках — 16 мс, всё заменено. 40×20×40 = 32 000 клеток — 16 мс.
- Предел движка — **ровно 32 768 клеток на вызов**, и это не оценка, а текст ошибки: `Dimension.fillBlocks: Cannot perform a single fill greater than [32768] blocks`. 33×32×32 = 33 792, 40×21×40 = 33 600 и 40×30×40 = 48 000 отвергнуты за 0 мс, ни одна клетка не тронута.
- Выбранный запасной путь: объёмы больше 32 768 клеток режутся на вызовы ≤ 32 768 клеток, например 40×30×40 → слои по 40×20×40. Схему это не меняет, это деталь `L0-strf-p003`.

### Q11 — `/tickingarea add` через `runCommand` · PASS

- Измерено в мире без игрока (bds:check): `tickingarea add circle … 2` в 500 блоках → `successCount=1`. До этого чанк был не загружен, после загружен за **17 тиков / 759 мс** (запуск 1) и **19 тиков / 853 мс** (запуск 2). Прежний прогон PRB-CHUNK-01-AA дал 15 тиков / 651 мс. `remove` разгружает за **1 тик**. Предел — **10 областей**, одиннадцатая отвергается (`successCount=0`).
- В мире GameTest та же команда загрузила чанк за 2 тика / 99 мс, а предел был **9**: одну область, видимо, держит сам GameTest-мир. Реальное число для аддона — 10, из мира без чужих областей.
- Круг радиуса 2 даёт загруженный крайний чанк (+32 блока), а в 4 чанках от центра уже не загружено.
- Не измерено: максимальный размер одной области. ADR wind-ad01 предполагает ≤ 100 чанков (≤ 10×10), но зонд проверял только круг радиуса 2 (5×5 чанков).

## Отдельные находки о движке

- **`getPackStructureIds()` не видит пакетные структуры.** В мире без игрока (bds:check) он возвращает `[]`, хотя `world.structureManager.get("andrew:probe_box")` и `get("andrew:probe")` работают (selftest `structure-probe-box` PASS). В мире GameTest возвращает только `andrew:platform` (структура GameTest-пакета), без `andrew:probe_box`. Регистрацию структуры проверять только через `get(id)`.
- **`getAllStates()` у перестановки из шаблона** (`Structure.getBlockPermutation`, до установки в мир) у двери вернул `{}`. У сундука и визгуна состояния читаются. `getState("upper_block_bit")` у той же двери работает (selftest `structure-probe-box` PASS). Из прогона PRB-TMPL-01-AA: состояния для сравнения поворотов читаются с блоков, **поставленных в мир** (так и делает Q2).
- **`successCount` у `/loot insert` не доказывает заполнение** (Q4, полный сундук).
- Блок двери дуба в 1.26.51 называется `minecraft:wooden_door`. `minecraft:oak_door` не существует, и движок загружает его как неизвестный блок без состояний (PRB-TMPL-01-AA, `src/selftest/main.ts`).

## Решения по ADR
